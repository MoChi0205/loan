# check-kb-consistency.py · 知识库 / 代码一致性校验

一个**只读**的一致性校验脚本，把「代码即唯一真值」的 5 项断言固化下来，
防止文档与代码再次脱节（本轮治理中靠人肉 grep 才发现：表数 65/66 vs 实际 68、
渠道角色 tab 数 3 vs 实际 4、文档引用不存在的 `output/` 目录）。

- 主脚本：`scripts/check-kb-consistency.py`
- 说明文档：本文件
- 语言：python3（仅用标准库，无第三方依赖）

> **规范性依据**：本脚本涉及「是否写死某个值」的取舍，一律遵循**规则 9**，
> 其**唯一权威表述**在 `docs/knowledge-base/10-历史结论与决策日志.md` 的 **D15** 条目
> （含三类例外：恢复锚点 / 纠错证据 / 已执行动作记录，以及判据）。
> **本文件不重述规则 9，只说明脚本行为**；需要引用规则时请直接引 D15，
> 不要从本文件转述，避免规则在复述中变形。

---

## 一、怎么跑

```bash
# 全量检查（可从任意工作目录运行，脚本用自身位置推导仓库根）
python3 scripts/check-kb-consistency.py

# 只输出汇总，不展开差异明细
python3 scripts/check-kb-consistency.py --quiet

# 只跑指定检查项
python3 scripts/check-kb-consistency.py --only 1,4
```

建议接入日常流程：

```bash
# 改完文档或代码后自查
python3 scripts/check-kb-consistency.py --quiet || echo "文档与代码已脱节，请修复"

# 作为 git 提交前门禁（复制到 .git/hooks/pre-commit 或由 CI 调用）
python3 scripts/check-kb-consistency.py
```

### 退出码

| 退出码 | 含义 |
|--------|------|
| `0` | 无 FAIL（全部通过，或全部因源文件缺失而跳过） |
| `1` | 存在至少一项 FAIL —— 可直接用于 CI / pre-commit 拦截 |

## 二、五项检查的含义与修复方式

### 检查 1 · 表数一致性

- **真值**：`db/loan-db-schema.sql` 中 `CREATE TABLE` 的出现次数。
  **由脚本每次运行时动态统计**；本说明不写死具体数字，需要当前值时看脚本输出的
  「真值」行（依据规则 9，规则正文与三类例外见 **D15**，本文件不另作表述）。
- **做法**：扫描 `docs/` 下所有 `.md` / `.html`，用正则找「N 表 / N 张表」表述，
  与真值比对，报出 `文件:行号 | 实际值 | 期望值 | 原文`。
- **降噪规则**（避免误报）：
  - 数字 < 20 → 视为增量/局部表述（如「新增 2 张表」「跨 3 表」），跳过；
  - 数字前 12 字符内出现 `新增/追加/涉及/跨/合表` 等 → 视为增量表述，跳过；
  - 数字前出现 `原/历史/早期/曾经` 等 → 视为历史叙述（如「原 61 表清单」），跳过；
  - **同一行内已出现正确表数、或带勘误说明** → 降级为 `WARN`（不阻塞 CI），
    但仍建议直接改写正文、删掉旧数字，而不是保留「65→66 表 + 勘误」的写法；
  - **受保护行**（对应 **D15 三类例外**，见 `docs/knowledge-base/10-历史结论与决策日志.md`
    的 D15 条目）→ 降级为 `WARN`，并显式标注「**属受保护信息，请勿改写此行数值**」：
    - ① 恢复锚点（`git 基线`/`恢复锚点`/`备份`/`b80c965a` 这类 hash）；
    - ② 纠错证据（`纠错证据`/`是错的`/`实测为`/`时点真值`）；
    - ③ 已执行动作记录（`归档 N 个文件`/`重号修复`/`已落`）。
    
    这是 D15 三类例外的自动化护栏：这类行引用旧值恰恰是为了证明「曾经错过」或
    「做过什么」，改写它反而会摧毁不可逆事实。**脚本只保护、不改写**——
    修复动作一律交给人判断。

### 检查 2 · 角色 tabBar 数量一致性

- **真值**：解析 `loan-mini/components/TabBar.vue` 中 `tabList` 计算属性——
  `store.isChannel` 分支（渠道）与默认分支（客户/员工）返回的数组长度与标签。
  **同样由脚本运行时解析，本说明不写死 tab 数**（依据规则 9，见 D15）。
- **做法**：扫描 `docs/` 找「N tab」表述，按**距离最近**的 `渠道/客户/员工` 关键词
  判定其所属角色，与真值比对。
- **降噪规则**：
  - 处理「非渠道」「其余/其他」→ 自动映射到对立角色；
  - 排除 `「录入客户」` 这类 **tab 名**被误判为角色关键词（检查标签上下文字符）；
  - 整行出现 `不一致/待修正/勘误/以 TabBar.vue 为准/文档错误` 等
    「已自证为已知问题」的行 → 跳过（它是在描述问题，不是在断言）；
  - 同样跳过**受保护行**（D15 三类例外，标记清单同检查 1），避免把
    「文档曾写 3 tab、实测 4 tab」这类纠错证据当作新脱节处理。

### 检查 3 · 业务包实现状态

- **做法**：统计 `loan-service/src/main/java/com/loan/` 下每个业务包的 `.java` 文件数。
- **关键：空包不一律判「无实现」** —— 先在全仓按文件名做同名/相关类搜索，区分两类：
  - **真空包（无实现）** → `FAIL`：全仓都找不到同名/相关类，应删除目录或补实现；
  - **⚠️ 包名与实现位置不一致** → `WARN`（不计入退出码）：实现散落在其它包，
    脚本会输出具体位置（如 `match` 包为空、实现在 `engine/service` 等处）。
- 空包清单同样**以脚本实际输出为准**，本说明不写死包名与数量（依据规则 9，见 D15）。

### 检查 4 · 文档指针死链

- **扫描范围**：`docs/knowledge-base/*.md`、`docs/skills/**/SKILL.md`、
  `.workbuddy/skills/**/SKILL.md`。
- **做法**：从反引号片段、markdown 链接目标、行内裸写路径中提取引用
  （**支持含空格的文件名**，如 `04-后端 API 契约.md`），逐个验证存在性。
- **解析顺序**：① 相对文档自身目录 → ② 相对仓库根 → ③ 去掉 `loan-main/` 等仓库名前缀再试
  → ④ 按路径后缀模糊匹配（文档常写模块内相对路径，如 `service.sh`、`src/layout/Layout.vue`）。
- **降噪规则**：
  - 跳过代码块（```）、ASCII 目录树示意行；
  - 跳过模板占位（`NN-模块名.md`）、URL、Java 包名（`com.loan.x`）、通配符；
  - 跳过构建产物路径（`dist/`、`build/`、`target/`、`app.json` 等，构建后才存在）；
  - 跳过报错原文里的路径（如 `` `ENOENT: src/manifest.json` ``）；
  - **跳过文档自身警示失效引用的行**（含 `禁止引用/不存在/已删除/失效` 等），
    这类行是护栏而非脱节 —— 注意这是**整行**级别的判断。
- **严重度**：文件引用失效 = `FAIL`；纯目录引用失效 = `WARN`
  （目录可能是「尚未创建的归档约定」，如 `requirements/`、`research/`）。
- 已知的 `output/` 前缀会额外提示「历史失效前缀，该目录已不存在」。

### 检查 5 · 接口契约一致性

- **真值**：`loan-service` 中所有 `*Controller.java` 的 `@RequestMapping` /
  `@*Mapping` 实际路径（类级 + 方法级按 Spring 语义拼接）。
- **做法**：从 `docs/knowledge-base/04-后端 API 契约.md` 提取接口路径，双向比对：
  - **文档有而代码没有** → `FAIL`（接口已下线或路径写错）；
  - **代码有而文档没写** → `FAIL`（新增接口未同步契约）；
  - **占位符命名不一致** → `WARN`（如文档 `{code}` vs 代码 `{clientCode}`）；
  - **文档写死具体值、代码用路径变量** → `INFO`（如 `ALLOCATION` vs `{type}`）；
  - **已废弃（~~删除线~~ 标记）路径** → `INFO`，报告其现状
    （兼容期仍存在 / 已移除），不重复计入差异。
- **作用域**：文档标题与 Base URL 声明其覆盖小程序端，故「代码有而文档没写」
  只统计文档中**自动识别的、占比最高的前缀**（脚本输出的「文档声明作用域」即为当前值，
  文档前缀结构变化时自动跟随），避免把管理端全量接口算作漏写噪音。
- **路径等价判定**（`paths_match`）：段数相同，且每段相等 / 两段都是占位符时等价；
  占位符 vs 字面量时，**仅当字面量全大写**才等价（`ALLOCATION` ↔ `{type}`）。
  否则 `/order/{orderNo}` 会被误判为等价于 `/order/list`。

## 三、输出格式

每项检查一个分节，形如（**以下为格式示例，数值与差异条数随代码/文档变化，非当前快照**）：

```
==============================================================================
检查 2 · 角色 tabBar 数量一致性（真值：loan-mini/components/TabBar.vue）
==============================================================================
  真值：渠道（store.isChannel）= 4 tab [...]；客户/员工（默认）= 5 tab [...]
  结果：FAIL（9 处差异）

  【FAIL】9 条
    · docs/knowledge-base/01-角色权限模型.md:74
        实际值：渠道 3 tab
        期望值：渠道 4 tab
        说明  ：原文：- **渠道**：3 tab（首页·我的产品·我的），隐藏匹配/报告/服务单；...
```

- `FAIL`：真实脱节，**影响退出码**；
- `WARN`：轻度不一致或约定性缺失，需人看一眼，不影响退出码；
- `INFO`：符合预期的现状说明（如废弃接口兼容期），纯展示；
- `SKIP`：依赖的源文件不存在，跳过该项。

末尾汇总 `X/Y 项通过`、未通过项清单，并给出**逐项修复建议**。

## 四、设计约定

1. **只读**：脚本不修改任何被检查的文件，可放心反复执行。
2. **编码安全**：统一 `utf-8` 读取，非法字节降级替换（`errors='replace'`），
   中文文件名/内容不会导致崩溃。
3. **容错**：单个检查抛异常不会中断整轮校验，该检查记为执行异常；
   源文件缺失则 `SKIP` 并提示。
4. **可扩展**：新增检查只需写一个返回 `CheckResult` 的函数，
   并加入 `main()` 的 `(check_id, runner)` 列表与 `FIX_SUGGESTIONS` 字典。

## 五、已知边界

- 检查 1 只对「N 表」类表述生效，不解析 `t_xxx` 表名清单与 schema 的逐表比对。
- 检查 4 的「文档自证失效」是**整行判断**：一行里若既有失效引用、
  又写了「不存在」字样，整行都会被跳过 —— 这也是为什么注入验证时要避开这类措辞。
- 检查 5 只做**路径**比对，不校验请求/响应字段与权限注解。
