# 后端接口、并发、稳定性与日志标准

## 1. 接口与查询设计

- 同一资源统一查询模型：单条详情、批量查询、组合条件分页各有清晰入口，底层复用同一 Query DTO / Specification / Wrapper 构造器。
- 禁止每增加一个查询条件就新增一个方法（如 `findByName/findByStatus/findByNameAndStatus`）。可组合条件放入查询 DTO，只允许对有独立业务语义、权限或性能模型的查询单独建接口。
- 批量入参去重、限制最大数量、一次批量查库/RPC；禁止循环内逐条查询。结果用 `Map<BizCode, DTO>` 或按请求顺序的 List 返回，并明确未命中项语义。
- 列表默认分页，限制 `size` 上限；排序字段使用 `PageOrder` 白名单，筛选/排序列需核对索引。禁止无上限全表返回。
- 单条查询按业务编码，不对外暴露自增 ID；批量与分页同样使用业务编码。详情、修改、删除等单资源接口均以业务唯一编码定位；更新请求不得接收或改写业务编码，数据库物理主键只允许在持久层内部使用。
- Controller 只做协议解析、入参校验与授权边界；业务编排在 Service，数据访问在 Mapper/Repository。

## 2. 幂等、事务与并发

- 创建、提交、审批、支付、奖励、回调、批处理等重要写操作必须设计幂等键、业务唯一索引或状态机 CAS；相同请求重放不得产生重复业务记录或重复副作用。
- 严禁无保护的“先查再写”。同库关键更新优先唯一索引、条件 `UPDATE`、乐观锁/`version` 或 `SELECT ... FOR UPDATE`；跨进程互斥才使用 Redis 分布式锁。
- 分布式锁必须有唯一 owner token、过期时间、原子解锁，并考虑业务执行超时与续期；禁止直接 `DEL` 他人锁。
- 共享可变状态必须线程安全；优先不可变对象、方法内局部状态和并发容器，禁止在 singleton Service 保存请求级可变数据。
- 事务边界覆盖必须的数据原子性，不在长事务内调用慢 RPC；外部副作用使用可重试事件/outbox 或明确补偿，不伪装成本地事务。

## 3. 缓存与性能

- 稳定、读多写少、可容忍短暂旧值的数据可用 Caffeine 短 TTL + Redis 长 TTL 二级缓存。高频更新、强一致、高基数或敏感数据不得默认入缓存。
- 缓存 key 包含应用/业务域/版本/业务编码；值有明确 TTL、序列化版本和容量上限。
- 更新成功后失效本地与 Redis 缓存；跨节点本地缓存通过 Redis pub/sub/版本号/事件失效。不能只清当前 JVM。
- 防护穿透（入参校验+空值短缓存）、击穿（single-flight/互斥回源）、雪崩（TTL 抖动+容量限制）和大 key/热 key。
- 优化前后保留可观测证据：延迟分位数、QPS、命中率、DB/RPC 次数和错误率；禁止仅以“加了缓存”宣称性能提升。

## 4. 异常、稳定性与安全

- 业务可预期失败抛 `BusinessException + ResultCode`；由统一 `@RestControllerAdvice` 转为 `Result`。Controller 不大量 `try/catch`、不吞异常、不伪返回成功。
- 参数、认证、授权、业务异常和未知系统异常分类映射稳定错误码；未知异常对外只返回友好文案 + traceId，堆栈只记 error 日志。
- 限流/限频按主体+端+接口+业务 key 配置；登录、短信、上传、查重、匹配、导出、审批等高风险/高成本接口必须有专项策略。返回统一“请求过于频繁”错误结果。
- 外部 HTTP/RPC 必须设超时、并发隔离和熔断降级。只对幂等操作做有上限、带抖动的重试；禁止无界重试和对非幂等写操作自动重试。
- 限流/熔断必须有监控指标、告警、可配阈值和降级语义；不在业务代码散落魔法数字。

## 5. traceId 与日志

- 网关接受/生成 traceId → 请求头透传 → 各应用放入 MDC → `Result.traceUuid` 返回 → HTTP/RPC/异步任务继续透传。线程池任务必须显式复制并在 finally 清理 MDC，防止串请求。
- 业务日志与异常日志分流：`logs/{yyyyMMdd}-{application}-{service}-biz.log`、`error/{yyyyMMdd}-{application}-{service}-error.log`。同时按日期和单文件大小滚动，配置保留天数、总容量上限与压缩归档。
- 中文结构化格式示例：`渠道策略分页接口-入参={}，查询结果摘要={}，耗时={}ms，traceId={}`。记录接口/业务动作、业务编码、数量/状态摘要与耗时，不记整个大列表/大对象。
- 参数和结果必须脱敏：禁止记录 token、密码、secret、完整手机号/证件号/银行卡、原始文件、AES 明文、完整 OCR 内容。
- info 记录关键业务节点，warn 记录可降级/可恢复异常，error 记录未知系统异常并携带堆栈。不重复在每层打同一堆栈。

## 6. 后端验收清单

- [ ] 单条/批量/分页是否复用统一查询模型，无 N+1，分页有 size 上限？
- [ ] 详情/修改/删除是否按业务唯一编码定位，更新请求是否禁止接收物理主键和改写业务编码？
- [ ] 重要写接口是否幂等，状态迁移与锁是否可并发验证？
- [ ] 缓存是否有适用证据、TTL、容量上限、双层失效与穿透/击穿/雪崩保护？
- [ ] 业务/系统异常是否统一返回，是否存在吞异常/伪成功？
- [ ] 高风险/高成本接口是否有限频，外部依赖是否有超时、隔离、熔断和安全重试？
- [ ] traceId 是否跨网关/HTTP/RPC/异步线程透传，MDC 是否清理？
- [ ] 日志是否中文可检索、按日期+大小切分、biz/error 分流、参数脱敏且结果只记摘要？
