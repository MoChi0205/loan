# 前端复用、契约与可理解数据展示标准

## 1. 分层与复用

- 页面只组合业务流程与页面状态；HTTP 契约放 `api/`，通用状态放 store/composable，无副作用格式化/校验放 `utils/`，复用交互放 `components/`。
- 新建页面前查公共组件与 utils。查询栏、分页、表格操作、弹窗、确认、空态、状态字典、日期/金额/脱敏不得页面内各写一份。
- 同类页面不复制整页改字段；使用可配表格/表单、composable 或业务子组件，差异通过 props/slots/schema 表达。
- API 方法以资源与动作命名，不把 URL、token、错误处理散落在页面；同一资源的单条/批量/分页参数语义与后端保持一致。
- 防止重复提交：写操作有 loading/按钮禁用，不只依赖前端防重，后端仍必须幂等。

## 2. 用户可理解展示

- 界面主位展示用户能理解的中文名称、姓名、企业名、产品名、部门名、状态文案和业务描述。
- `userId/staffCode/clientCode/orderNo/reportNo/templateCode/strategyCode` 等内部或业务编码不得作为列表主标题、主按钮文案或唯一可见信息。
- 后端 DTO 应批量补齐 `xxxName`，前端不在行循环逐条请求名称。若契约只返编码，作为契约缺陷处理，不用“直接展示 ID”掩盖。
- 确有客服排查、审计、复制或精确搜索需求时，编码可作次要信息：小字/次要色/截断 tooltip/“复制编码”操作，不喧宾夺主。
- 枚举、布尔、时间、金额、比率、手机号等用统一字典/格式化/脱敏 utils，不直接展示数据库原值。
- 隐藏 ID 不等于改变契约：路由、查询、更新仍用业务编码，不回退使用自增主键。

## 3. 数据、性能与可维护性

- 大列表使用服务端分页、筛选和排序；输入搜索使用合理 debounce/取消前请求，防止旧响应覆盖新状态。
- 对同一参数的短时重复请求可做请求合并；不缓存敏感数据或无法正确失效的业务结果。
- 并发请求的 loading、错误、空态和取消状态必须可区分，不将接口错误渲染为“暂无数据”。
- 公共 utils 保持纯函数且有边界用例；组件 props/emits 语义稳定，不读写无关全局状态。

## 4. 前端验收清单

- [ ] 页面是否复用现有 API / composable / utils / 组件，重复逻辑是否已提取？
- [ ] 表格与详情主位是否展示中文名称/姓名/描述，而非复杂 ID？
- [ ] 名称是否由后端批量补齐，无行级 N+1 请求？
- [ ] 业务编码若必须可见，是否降为次要信息并提供 tooltip/复制？
- [ ] 列表是否服务端分页/排序，并发请求是否不会乱序回写？
- [ ] 写操作是否防重，错误是否与空数据明确区分？
