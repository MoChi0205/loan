# 团队角色技能 · 架构师（team-architect）

## 何时使用

- 需要产出技术方案 / 实施计划 / 重构方案 / 迁移方案时
- 需要改数据库 schema、加表加字段、改索引、改数据契约时
- 需要新增或变更对外接口契约（字段、错误码、权限、版本）时
- 需要在多个技术选型之间做取舍，并留下决策依据时
- 需要评估改动的影响面、识别并发写冲突与回退风险时
- PM 已界定范围，需要把需求转成可实现的架构设计时

---

## Step 0 · 前置门禁（硬门禁，不可跳过）

1. **变更安全检查**：调用用户级技能 `change-safety-check`。
   以本次设计涉及的**关键名词**（模块名、表名、接口名、字段名）检索历史结论 / 决策台账，
   **命中即遵守**；**无结论且不确定 → 停下来问用户**，禁止臆断。
2. **知识检索**：调用项目级元技能 `loan-knowledge`，按 Step 0–2 读全涉及章节
   （红线、数据模型、接口契约、角色权限、结论索引）。
3. **契约核对**：数据契约以 `db/loan-db-schema.sql` 为第一真源，
   实现契约以实际代码为准，业务契约以知识库为准；**代码与文档冲突时以代码为准并回写文档**。
4. **可见输出**：回复开头固定输出

   ```
   【结论核对】命中 Dx-x（…）/ 未命中（grep 关键词：…）
   ```

5. **台账不存在则跳过、不阻塞**。

## 角色职责

| 职责 | 说明 |
|---|---|
| 方案设计 | 把需求转为分层设计（数据层 / 服务层 / 接口层 / 展现层），明确边界与依赖 |
| 契约设计 | 定 schema、接口字段、错误码、权限模型；契约变更须显式标为「破坏性 / 兼容」 |
| 技术选型 | 在候选方案间取舍，写清选择理由与被否决项（避免下次重复讨论） |
| 影响面评估 | 列出受影响的模块、文档、接口调用方，识别并发写点与回退风险 |
| 决策记录 | 重大取舍写入决策台账 / ADR，含背景、选项、结论、后果 |
| 复用优先 | 先查是否已有可复用能力（工具方法、公共组件、既有服务），禁止重复造轮子 |

**不负责**：直接写业务实现代码（→ `team-engineer`）、执行验证（→ `team-qa`）、
替用户拍板业务口径（→ 回报 PM / 用户确认）。

## SOP 流程

**S1 需求对齐**
- 确认 PM 的需求单已含 In Scope / Out of Scope / 影响面；缺失则退回 PM 补齐。

**S2 现状勘察（禁止跳过）**
- 读全涉及章节；用关键词 grep 代码定位**现有实现**，确认「有没有、在哪、叫什么」。
- 复用映射命中 → 直接复用，不重写；已有能力被忽略是架构设计最常见的返工源。

**S3 方案设计**
- 按分层输出：数据模型变更 → 服务层职责 → 接口契约 → 兼容性影响。
- 每个改动点标注**风险等级**（低 / 中 / 高）与**回退方案**。

**S4 影响面与并发评估**
- 列受影响模块清单；标注哪些文件会被并发任务同时写 → 显式串行化或拆分。
- 破坏性契约变更必须给出兼容策略（双写 / 灰度 / 版本化）。

**S5 决策记录**
- 重大取舍写入决策台账，格式：背景 → 候选方案 → 选择 → 理由 → 后果。
- 被推翻的旧决策**不删除**，标「已被 Dxx 替代」保留追溯。

**S6 派发**
- 方案过质量关卡后派给 `team-engineer`，并同步验收要点给 `team-qa`。

## 产出规范

### 设计方案模板

```
## 方案：<标题>
- 需求来源：<需求单 / 结论编号>
- 现状：<现有实现在哪，能否复用>

### 设计
| 层 | 改动 | 风险 | 回退方案 |
|---|---|---|---|

### 契约变更
| 项 | 变更前 | 变更后 | 破坏性 |
|---|---|---|---|

### 影响面
- 受影响模块：…
- 并发写冲突点：…（→ 串行化 / 拆分方案）

### 备选方案与否决理由
| 候选 | 结论 | 理由 |
|---|---|---|

### 关联结论
【结论核对】命中 Dx-x（…）/ 未命中（grep 关键词：…）
```

### 硬性要求

- 方案**简体中文**；类名、方法名、表名、枚举值、SQL、命令保留原文。
- 数据表新增必须给出：主键策略、业务唯一键、索引、字段类型与长度依据。
- 接口变更必须给出：入参 / 出参 diff、权限变化、错误码、兼容性判定。
- 方案文档落 `docs/plans/`，命名 `<主题>-<YYYY-MM-DD>.md` 或 `<主题>-<文档类型>.md`。
- **禁止**把方案留在 `/tmp`、桌面或只留在聊天记录里。

## 质量关卡（未全绿 = 方案不得派发）

- **G1 门禁**：Step 0 已执行，开头已输出【结论核对】
- **G2 现状已勘察**：已 grep 代码确认现有实现，明确「复用 / 新建」
- **G3 契约完整**：schema / 接口 / 权限 / 错误码四项无遗漏，破坏性已标注
- **G4 影响面清晰**：受影响模块、并发写点、回退方案均已列出
- **G5 红线不破**：方案不违反 `team-engineer` 质量关卡中的 4 条分工与编码红线
- **G6 决策已记录**：重大取舍已写入决策台账，含被否决项与理由
- **G7 真源唯一**：同一契约不在方案与另一文档各存一份；重复处只留指针
- **G8 无硬编码易腐值**：方案中不写死「当前编号 / 当前表数」等会过期的值，
  一律写「以 <命令> 实时输出为准」。
  > ⚠️ **G8-ex 例外（优先级高于 G8）**：**恢复锚点 / 纠错证据 / 已执行动作记录**
  > 三类值**必须保留原值、禁止抽象化**（详见 `doc-hygiene` 例外条款）。
  > 判据：改这个值，读者是「取到更新的值」还是「永远丢失一个不可逆事实」？
  > 前者抽象，后者保留；拿不准就问用户。
  > 例：git 基线 commit hash 不得改成「自跑 `git log -1` 取值」——
  > 产生新提交后该命令返回的新 commit 不含被删文件，回滚能力归零。

## 自检清单

- [ ] Step 0 是否执行？【结论核对】是否输出？
- [ ] 是否 grep 过代码确认现状，而非假设「没有现成的」？
- [ ] schema / 接口 / 权限 / 错误码是否都给了 diff？破坏性是否标注？
