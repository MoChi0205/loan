# Loan 系统分角色页面/API 权限审计报告

- 审计日期：2026-09-28
- 审计对象：`loan-web`、`loan-service`、`loan-gateway`、Nacos `prd` 所指向的权限数据库
- 测试角色：`BOSS`、`ADVISER`、`DEPT_MANAGER`、`OPERATOR`、`SUPER_ADMIN`、`SUPER`、`CHANNEL`
- 执行口径：真实账号登录、真实菜单树、业务服务只读接口矩阵、权限表核对、代码反向审计
- 数据安全：本轮未新增、更新或删除业务数据，未修改业务代码

## 一、结论

当前权限体系尚不能作为上线验收通过。已确认 **2 个 P0、6 个 P1、2 个 P2** 问题；最严重的是客户对象级权限缺失，以及业务服务可直连导致网关不再是不可绕过的安全边界。

| 等级 | 数量 | 结论 |
|---|---:|---|
| P0 | 2 | 上线/开放非可信网络前必须关闭 |
| P1 | 6 | 页面、菜单、接口、数据范围存在漂移，应在一个权限迭代内完成 |
| P2 | 2 | 存在不必要授权与稳定性风险，应随权限整改一并收口 |

已验证的正向控制：普通客户列表和详情手机号均为 `139****0031` 形式，响应未发现 `phone_plain`；渠道 `/api/auth/me` 的 `userNo` 为哈希值；日志查询参数手机号已脱敏；Web 菜单/路由/业务 ID 定向测试 15/15 通过；后端现有权限定向测试通过。

发布门槛建议：先关闭 P0，再完成“菜单路径—页面按钮—API—数据范围”四层一致性测试；完整矩阵必须经 `9088` 网关复跑，不得只以 `9080` 业务服务结果作为验收结论。

### 2.2 测试边界

1. `9080` 是业务服务直连端口，`9088` 才是网关；本轮真实请求期间 `9080` 可用，随后两个端口均停止监听，因此完整网关矩阵尚未补跑。
2. 业务服务结果用于发现业务层授权缺陷，不能替代网关验收；网关恢复后必须使用相同 7 角色矩阵复测。
3. 当前数据仅有无归属客户 1 条、`ADV001` 归属客户 32 条、其他员工归属客户 0 条，无法用现有数据证明经理跨部门客户列表隔离。
4. 分配、下载、产品审批当前无待审记录；审批部门范围问题来自代码审计，需补专用跨部门测试数据后动态验证。
5. 顾问服务运营 `DEPARTMENT/COMPANY` 范围曾在运行实例返回成功，但当前源码、字节码和定向单测均应拒绝；该项标记为“运行实例与当前构建不一致”，重启当前构建后经 `9088` 复测，不直接判定为当前源码漏洞。

## 三、权限缺陷清单

### AUTH-P0-01：客户详情、历史和编辑缺少对象级权限

> 整改状态（2026-09-28）：代码已修复，待应用重启后通过 `9088` 网关执行真实角色验收。新增统一 `ClientAccessGuard`，详情/历史走只读守卫，编辑在事务内执行写守卫并锁定客户记录；权限定向测试及 `loan-service` 全量 446 项测试均通过（1 项既有 L3 测试跳过）。

| 字段 | 内容 |
|---|---|
| 角色 | ADVISER、DEPT_MANAGER、BOSS、OPERATOR、SUPER_ADMIN、SUPER |
| 页面/接口 | 客户详情；`GET /api/admin/client/{clientCode}`、`GET /api/admin/client/{clientCode}/history`、`PUT /api/admin/client/{clientCode}` |
| 复现 | 顾问携带本人合法 JWT，直接把 URL 中 `clientCode` 替换为 `svtest_031` |
| 实际 | 详情与历史返回成功；编辑接口进入更新服务，Controller 未校验对象归属。本轮未执行写请求，避免污染数据 |
| 期望 | 顾问仅可访问本人客户；经理仅本人/本部门；老板、运营、超管按已定义公司范围；不可见对象统一返回 403 或 404 |
| 原因 | 列表接口计算了 `scope`，但详情、历史、编辑仅按 `clientCode` 查询，没有复用客户可见范围守卫 |
| 风险 | 横向读取客户档案、企业资料、画像与流转历史；编辑接口存在潜在跨客户写入风险 |
| 证据 | `ClientController.java:209-213,304-319`；顾问真实请求 `svtest_031` 成功 |

修复要求：建立统一 `ClientAccessGuard.requireReadable/requireWritable(user, clientCode)`；详情、历史、编辑、材料、报告、服务记录全部复用，不能由前端列表是否展示决定。

### AUTH-P0-02：业务服务可直连，权限过度依赖网关

| 字段 | 内容 |
|---|---|
| 角色 | 全部角色 |
| 页面/接口 | `9080` 上全部业务接口 |
| 复现 | 绕过 `9088`，使用合法 JWT 直接请求 `http://服务地址:9080/loan/api/...` |
| 实际 | 203 个只读请求由业务服务直接接收并处理；部分接口只有角色/API 校验，没有完整对象级校验 |
| 期望 | `9080` 仅允许网关/可信内网访问；业务层对认证、API 权限和对象范围仍应 fail-closed |
| 原因 | 部署网络边界与应用内权限没有形成双重约束，网关成为可绕过的主要授权层 |
| 风险 | 一旦端口暴露或内部网络被利用，可跳过网关的角色×接口×客户端规则 |
| 证据 | 本轮全部真实请求均通过 `9080` 完成；客户详情对象级校验缺失已被同轮证实 |

修复要求：网络层封闭 `9080`；业务服务验证网关可信身份/签名；除公开登录、健康检查外默认要求认证，并保留对象级权限，不能只依赖网络隔离。

### 稳定性附带问题：Redis 超时放大权限接口失败

`logs/error.log` 在 2026-09-28 06:58 多次出现 `RedisCommandTimeoutException: Command timed out after 10 second(s)`。权限规则、会话和网关判断依赖 Redis；10 秒超时会把权限正确性问题表现为页面白屏、403 或首屏并发失败。该问题不改变上述授权结论，但会阻塞稳定复测，应在权限回归前先确认 Redis 网络与连接池状态。

## 四、角色/页面/API 矩阵摘要

| 角色 | 页面范围（按真实菜单） | 应有数据范围 | 本轮主要异常 |
|---|---|---|---|
| ADVISER | 工作台、本人线索/客户、公司公海、服务、申请等 | 本人；经确认的公海可见对象 | 可凭 clientCode 读取其他客户详情/历史；审计/config 授权偏宽 |
| DEPT_MANAGER | 顾问能力 + 团队客户/服务/审批 | 本人 + 本部门；审批仅本部门 | 统一审批多类型未传部门范围；组织/权限查询过宽 |
| BOSS | 全司业务、经营分析、审批 | 本人 + 全公司，系统配置受限 | TEAM 菜单与接口冲突；依赖 deny-list，新增接口易自动放行 |
| OPERATOR | 全司运营页面 | 本人 + 授权的公司运营数据 | 菜单未授权接口仍因 superRoles 全量放行；TEAM 菜单失败 |
| SUPER_ADMIN / SUPER | 全司业务与系统管理 | 全公司 | 全量 API 符合角色方向，但仍受客户对象守卫缺失影响；TEAM 菜单语义错误 |
| CHANNEL | 工作台、初筛及渠道业务父模块 | 仅本渠道数据 | 快捷入口叶子路径不在真实菜单，可能被路由守卫拒绝 |

一致性判断：当前“菜单可见”既不能证明“接口可用”（TEAM 客户、渠道快捷入口），也不能证明“接口不可用”（superRoles、报告路由兜底）；“列表范围正确”也不能证明“详情对象安全”（客户详情/历史/编辑）。

现有定向测试结果：后端权限测试通过；Web 菜单、路由、业务 ID 测试 15/15 通过。这说明已有测试覆盖了静态菜单/路由规则，但未覆盖“跨角色直接调用对象详情”“菜单与真实 API 同步”“审批跨部门数据”三个关键反例。

## 五、阻塞与修复顺序

1. **先关闭对象越权（0.5～1 个开发日）**：统一客户对象访问守卫，覆盖详情、历史、编辑及所有下游材料/报告/服务接口；补本人、本部门、跨部门、无归属、公海被领取后的用例。
2. **封闭直连与默认全量（0.5～1 个开发日）**：限制 `9080` 网络来源；只保留 SUPER_ADMIN/SUPER 的明确全量能力，BOSS/OPERATOR 改 allow-list，新接口默认拒绝。
3. **统一菜单/页面/API（1 个开发日）**：删除报告路由兜底；修正 TEAM 和渠道快捷入口；生成“每个叶子菜单 → 首屏接口 → 按钮接口”契约测试。
4. **收口审批与辅助查询（1～2 个开发日）**：审批查询强制传当前用户和部门范围；以精简员工/部门选择器替代完整组织权限接口；删除工作台无用 `config/status` 请求。
5. **完成网关验收（约 30～60 分钟执行时间）**：使用当前构建、显式 Nacos `prd` 启动应用，经 `9088` 对 7 角色复跑同一矩阵；补两部门客户和审批数据，仅在隔离测试数据中执行写操作；核对 Redis 超时后再下最终结论。

最终通过标准：无菜单页面不可进入、无按钮操作不可直调、越权 API 返回 403、不可见业务对象按角色范围拒绝、经理审批不跨部门、渠道仅本渠道、客户端响应无明文敏感字段，并且同一结论在 `9088` 与业务层对象守卫同时成立。
