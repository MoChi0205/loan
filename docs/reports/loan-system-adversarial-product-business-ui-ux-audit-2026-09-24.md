## 三、业务流程反方审查

### 3.1 外出流程按最终确认执行

本轮已确认最终口径：**外出必须主管审批；出发和返回都必须打卡；照片必填；单点位置必填；不采集连续轨迹**。当前实现创建后进入 `PENDING_REVIEW`，审批通过后进入 `READY`，打卡时同时校验照片和定位，已与最终口径一致。

证据：

- [`OutingService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/serviceops/service/OutingService.java:119) 创建后写入待审核，并记录“待主管审核”。
- [`OutingStateMachine.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/serviceops/model/OutingStateMachine.java:8) 固化审批状态机。
- [`ServiceOperations.vue`](/Users/admin/Downloads/loan-main/loan-web/src/views/service/ServiceOperations.vue:110) 仍展示审核人、通过和驳回操作。
- [`客户画像与预约外出跟进三端联动技术方案`](/Users/admin/Downloads/loan-main/docs/plans/客户画像与预约外出跟进三端联动技术方案-v1-2026-09-21.md:114) 也是旧审批口径。

仍需反方检查的不是“是否审批”，而是审批时效和异常补救：审批人离线时是否允许紧急代审、驳回是否必须说明原因、照片上传成功但打卡失败时如何清理无主附件。

验收标准：普通顾问创建外出进入待审核；经理通过后才能出发打卡；出发和返回均拒绝无照片或无定位请求；位置只保存两个打卡点，不生成连续轨迹。

### 3.2 预约确认规则已按创建方拆分

旧实现和旧审计曾把两类预约混为一谈。本轮已按最终业务确认拆分：

- 客户主动预约：状态 `REQUESTED`，客户意图记录为已提交，等待服务顾问接单。
- 员工代客预约：状态和确认状态均为 `CONFIRMED`，客户无需确认，员工无需二次确认。

小程序已移除员工代建预约的客户确认按钮；Web 不再显示员工“确认预约”操作。客户主动预约仍保留顾问接单路径。

建议采用唯一规则：

| 创建方 | 初始状态 | 谁做下一步 |
|---|---|---|
| 客户发起 | `REQUESTED` + 客户已提交 | 顾问接单后转 `CONFIRMED` |
| 员工代客创建 | `CONFIRMED` + 公司已确认 | 直接进入后续履约，不再确认 |

验收标准：员工代建预约创建响应即为 `CONFIRMED`；客户端不出现确认按钮；客户主动预约只显示“等待顾问确认”。

### 3.3 普通外出与客户上门已拆分

本轮已按业务确认拆分：外出可以关联已确认的 `HOME_VISIT` 预约，也可以使用 `GENERAL` 类型，不关联客户或预约。普通外出必须本人填写计划时间、目的地和事由，仍需主管审批、照片和单点位置双打卡。

数据模型现已将 `appointmentNo/clientCode` 改为可空；上门预约自动带入客户和地址，普通外出由员工手工填写。渠道角色仍完全排除。

### 3.4 预约可选时间是假可用时间

客户目前可选任意日期时间，提交时才校验员工冲突；系统未表达营业时间、节假日、顾问排班、服务容量、提前预约上限和预约间缓冲。

反方场景：客户填写全部信息后才收到“顾问已有预约”；夜间或休息日也能提交；连续预约之间没有通勤时间。

整改方向：先提供服务端可用时段接口，再由小程序展示可选时段；冲突校验仍在提交时二次执行，避免并发抢占。

### 3.5 服务地点责任不清

`COMPANY_ON_SITE` 与 `HOME_VISIT` 都要求客户输入地点。客户到访公司时，公司地点应来自门店/组织配置；员工上门时才由客户确认服务地址。

反方场景：客户把自己家地址填到“到公司现场”，员工看见错误来访地点；或客户输入任意公司地址，造成错店到访。

验收标准：到公司现场只选择门店；上门拜访选择或新增客户地址，并明确用途、可见人员和保留期限；视频会议与电话咨询不显示地点字段。

## 四、权限、安全与隐私审查

### 4.1 服务端口可绕过统一鉴权

初始审计发现 [`SecurityConfig.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/config/SecurityConfig.java:37) 使用 `.anyRequest().permitAll()` 且 JWT 过滤器会继续放行缺少 token 的请求。本轮已在服务过滤器增加直连拒绝：非公开接口无有效会话直接返回 HTTP 401；Spring Security 的 `permitAll` 仅保留为兼容自定义 `UserContext`。

攻击者视角：只要服务端口被错误暴露、反向代理绕开网关，或内部网络中的调用方直接访问，就可以探测 `/api/mini/**`、`/api/notification/**`、`/api/sms/**`、`/internal/**` 中遗漏的守卫。已有 `/api/admin/**` 和 `/api/channel/**` 拦截器并不能证明其他路径安全。

修复结果：服务层已默认拒绝；仅显式放行登录、验证码、健康检查、字典和确需公开的微信登录接口。网关是第一层，服务端是第二层，不能互相假设对方永远正确。

### 4.2 权限漏配会自动变成放权

初始审计发现 [`ApiPermissionService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/apiperm/service/ApiPermissionService.java:86) 默认 `loan.apiperm.strict=false`，代码注释也说明“无授权时保守放行”。本轮已改为默认严格模式；仍需在 Nacos 中补齐所有接口和角色授权，否则合法角色会得到 403，这属于有意的 fail-closed 行为。

反方场景：新增一个管理接口后忘记同步权限清单，菜单可能隐藏；现在接口会被拒绝而不是自动放权，但如果团队只修菜单不补权限，功能会出现 403。

验收标准：生产与共享开发环境均 fail-closed；接口未登记、角色未授权、菜单权限漏配分别返回可识别错误并写审计日志。

### 4.3 密钥配置未按红线安全失败

| 位置 | 当前行为 | 风险 |
|---|---|---|
| [`ApiPermissionController.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/apiperm/controller/ApiPermissionController.java:42) | 本轮已移除内部令牌默认值，改从 `app.gateway.internal-token` 读取并只接受请求头 | Nacos 缺失时启动失败；仍需确认远端值已配置 |
| [`AesUtils.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/infrastructure/security/AesUtils.java:35) | 本轮已移除 AES 默认值，缺失直接启动失败 | 需要在 Nacos 配置真实密钥并轮换旧开发密钥 |
| [`nacos/config/dev/application.properties`](/Users/admin/Downloads/loan-main/nacos/config/dev/application.properties) | 固定 JWT secret 可见 | 配置被复用或仓库泄露后可伪造 token |

整改结果：内部令牌和 AES 默认值已移除，内部令牌已改用请求头；缺少 Nacos 配置时启动失败。JWT secret 和 Nacos 中的开发密钥仍需由运维轮换，并确保不会复用到生产。

### 4.4 数据可见范围定义仍需做接口级验证

用户已确认的权限是：客户看本人；顾问看本人客户；经理看部门；老板、运营、超管看全公司；渠道完全排除。当前已有范围服务和部分 Controller 守卫，但仍需通过同一组契约测试验证列表、详情、导出、统计、搜索和聚合接口，不能只测页面菜单。

反方测试必须覆盖：顾问修改 URL 访问他人报告；经理跨部门搜索手机号；渠道 token 调员工接口；客户 token 调内部聚合接口；无 token 直连服务端口。

### 4.5 身份和敏感数据存储口径不一致

[`ClientProfile.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/client/entity/ClientProfile.java:96) 声明 openid 明文落库；[`WxCode2SessionService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/infrastructure/wechat/WxCode2SessionService.java:38) 又声称明文只在内存、落库只存 Hash；[`MiniAuthService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/mini/service/MiniAuthService.java:100) 实际同时写明文和 Hash。

建议：若无回显或调用微信接口的必要，只保留不可逆 Hash；如确需原值，应采用 AES 密文而非明文。手机号也不建议新增永久明文字段，应通过受控解密、默认脱敏、权限校验和查看审计满足员工查询需求。

## 五、报告、画像与合规隔离

### 5.1 双视角已具雏形，但不是完整隔离

当前已有员工聚合接口和权限前置检查，这是正确方向；但尚未形成方案中的客户独立端点、内部独立端点和 `CUSTOMER/STAFF` 双快照。当前仍依靠 DTO 选择字段和旧接口组合。

反方场景：以后为了员工页面增加“匹配产品、银行规则、内部建议”字段，若小程序复用了同一 DTO 或序列化对象，敏感字段会无意暴露给客户。

验收标准：

| 视角 | 允许内容 | 明确禁止 |
|---|---|---|
| 客户 | 经营事实、风险维度、材料完整度、经营优化建议、数据来源声明 | 银行名称、产品、准入规则、匹配结果、进件建议、通过概率 |
| 员工 | 客户画像、内部风险分析、渠道合作信息、可能适配产品、服务建议 | 对客户直接承诺审批结果或伪造授权来源 |

应建立独立 DTO、独立路由、独立权限测试和不可变快照；员工快照只能在员工端读取，渠道角色不可读取。

### 5.2 固定合规声明缺少事实校验

[`StaffReportAggregationService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/report/service/StaffReportAggregationService.java:38) 固定返回“仅使用客户主动填写及授权上传材料；未调用外部个人信息查询接口”。系统没有在返回前核验本报告对应的授权记录、授权范围和材料归属。

反方场景：授权记录丢失或材料由员工代传，报告仍显示同一声明。审计时只能看到文字，无法看到证据链。

整改目标：声明由事实生成；报告保存 `consentId/materialIds/sourceTypes/generatedAt`。缺少授权时不得生成带确定性措辞的正式报告，并向员工展示缺失原因。

### 5.3 画像 DTO 存在未来误复用风险

完整画像同时包含内部员工维度、风险、建议和客户摘要。即使当前页面只读取客户摘要，也应提供专用客户 DTO；“前端不显示”不是数据隔离，接口不返回才是隔离。

### 5.4 位置、照片和时间线保留规则未落地

规划提到保留期限，但尚未看到统一清理任务和明确配置。位置和现场照片属于高敏感服务凭证；无限期保存会放大泄露和内部滥用风险。

需一次性拍板：精确位置保留 30、90 或 180 天；到期删除密文和照片，只保留低精度审计结果与操作日志。时间线还应支持纠错留痕，不能覆盖原始记录。

## 六、Web UI、UX 与页面布局审查

### 6.1 菜单不是“层级清楚”，而是“标题和入口混在一起”

[`Layout.vue`](/Users/admin/Downloads/loan-main/loan-web/src/layout/Layout.vue:266) 在同一菜单中放入不可点击的 `isSection` 标题和可点击缩进项。线索管理、客户档案、服务台、短信服务、奖励管理、产品库、渠道管理、组织权限都使用这种模式。

反方体验：用户看到相同视觉权重的“标题”和“菜单”，不知道哪个能点；进入客户档案后，左侧也不容易确认自己处于哪个父级；这正是用户此前反馈“二级菜单标签与子标签区别不大”的根因。

建议结构只保留两层：

| 一级业务域 | 可点击子页面示例 |
|---|---|
| 客户经营 | 客户档案、团队公海、跟进记录、画像分析 |
| 服务履约 | 今日预约、来访名单、外出名单、服务工单 |
| 报告分析 | 报告中心、经营概览、趋势分析 |
| 渠道合作 | 合作方、合作产品、到期提醒 |
| 系统管理 | 员工、角色权限、接口权限、系统日志 |

所有子项必须是独立路由和独立页面；父级可折叠，但不可用伪标题冒充页面。

### 6.2 工作台缺少“现在该做什么”的排序

当前工作台同时展示今日服务、经营指标、待办、合作到期、快捷入口、最近匹配和主链路。信息很多，但行动优先级不清。

建议首屏只回答三个问题：今天要服务谁、哪些事项已逾期、哪个异常需要马上处理。经营总览和业务趋势下沉到第二屏或独立页面，成交趋势不得再次复制回经营概览。

看板卡片跳转应保留筛选上下文：点击“今日预约 8”后进入预约页，自动带入今天、当前权限范围和状态，列表明确展示客户、归属顾问、方式、地点、开始/结束时间和当前责任人。

### 6.3 页面表格密度和操作区需要统一

当前多张业务表同时使用状态标签、次要说明、固定操作列和多行文本。窄屏下会出现列压缩、状态下拉溢出和操作遮挡。

统一规则：搜索区最多两行；主身份列固定在左；状态与责任人靠前；低频字段放详情抽屉；操作列固定右侧但只保留一个主操作和“更多”；下拉层使用 Portal/Teleport 到 body 并限制高度和视口碰撞。

### 6.4 经营概览仍可能把缓存当作性能修复

已有 Caffeine + Redis 二级缓存，但缓存未命中时 [`ReportService.java`](/Users/admin/Downloads/loan-main/loan-service/src/main/java/com/loan/report/service/ReportService.java:151) 仍可能读取大范围工单号和客户号集合，再做多次统计。缓存只能降低频率，不能消除慢查询。

建议把稳定日统计落入按日期、部门、顾问维度的汇总表；当天实时数据增量计算；首页通过一个 BFF 聚合接口返回最小首屏数据。不得为了首页统计并行重复查询同一预约表。

## 七、小程序与 H5 交互审查

### 7.1 H5 登录首屏存在两个相互否定的主张

实页检查显示：H5 仍展示“微信一键登录”主按钮，同时页面提示 H5 应使用手机号验证码；另有“微信手机号一键登录”，普通用户无法理解两者差别。

整改后应是：

| 终端 | 主操作 | 备用操作 |
|---|---|---|
| 微信小程序 | 微信手机号一键登录 | 手机号验证码登录 |
| H5 | 手机号验证码登录 | 无微信小程序专属按钮 |
| Web 员工端 | 账号密码登录 | 手机验证码登录、验证码找回密码 |

### 7.2 登录首屏视觉资源用错位置

H5 Hero 高度过大，品牌标题重复，三步流程抢占首屏，真正的登录按钮被推到下方。登录页首屏应按“品牌一句话 → 主 CTA → 协议 → 合规说明”排列；三步介绍折叠或移到第二屏。

### 7.3 预约表单暴露实现概念，不是客户任务语言

小程序应让客户选择“到公司咨询、顾问上门、视频沟通、电话咨询”，而不是理解内部状态。到公司咨询应自动显示公司地址；顾问上门才填写地址；视频和电话隐藏地点。

取消或改期规则“到期前 5 分钟”应在选时间和列表操作处明确显示，而不是用户点击后才报错。

### 7.4 “下一步”字段语义错误

客户预约 DTO 的 `nextAction` 实际可能来自 `customerVisibleNote`。客户自己填写的“希望顾问准备什么”不能被页面显示为系统安排的下一步。

已拆成：`customerNote`（客户补充说明）与 `nextActionText`（服务端根据状态生成），旧 `nextAction` 仅保留兼容。客户端现在分别展示“你的补充说明”和“下一步安排”。

### 7.5 H5 无障碍与触控反馈不足

登录协议、分段标签、消息入口和快捷磁贴大量使用 `view/text + click`，缺少 H5 的按钮语义、键盘焦点和 Enter/Space 操作。拖拽、加载、空状态和失败重试也应有一致反馈。

验收标准：键盘可完成登录和主要导航；焦点可见；点击区域不小于 44×44；提交期间防重复；网络失败保留用户已填数据。

## 八、性能、稳定性与数据质量

| 编号 | 发现 | 反方场景 | 优化与验收 |
|---|---|---|---|
| PERF-01 | 工作台同时请求日服务列表和预约分页获取统计 | 同一首屏重复查预约数据 | 单一工作台聚合接口；一次返回总数与前 N 条 |
| PERF-02 | 报表缓存失效后存在大集合、多次查询 | 全公司管理员首次访问或缓存同时过期时卡顿 | 汇总表 + 分布式互斥/逻辑过期；记录 P95/P99 |
| PERF-03 | OCR/大模型识别可能同步占用上传线程，超时可达 60 秒 | 客户上传后长时间转圈、重试产生重复任务 | 上传立即返回任务号；异步识别；幂等与可重试状态机 |
| DATA-01 | 外出照片先上传、后提交打卡 | 打卡失败后留下无主附件 | 临时附件状态、提交绑定、定时清理和幂等键 |
| DATA-02 | 缓存写后失效覆盖面未形成验证矩阵 | 列表已完成，首页数字仍不变 | 每个写操作对应缓存键；契约测试验证读后立即一致或标明延迟 |

数据库关系使用业务编号作为逻辑关联是合理方向；自增主键仍可作为内部物理主键。要求应解释为“跨表业务关系、接口和日志不依赖自增 ID”，而不是强制删除所有自增主键，否则会损害索引和运维效率。

## 九、工程治理与测试缺口

### 9.1 当前测试通过不等于业务正确

本次验证结果：`loan-web` 6 个测试文件、27 个测试通过；`loan-service` 及依赖模块 Maven 编译通过。它证明当前改动没有明显破坏已有工具层行为和 Java 编译，但没有证明权限边界、三端状态机和字段隔离正确。

应补充的高价值测试：

1. 六类身份对同一列表、详情、导出、统计接口的权限矩阵。
2. 客户发起、员工代建、改期、取消、到访、服务完成的预约状态契约。
3. 有审批外出的出发/返回打卡、照片和位置保存、普通外出无客户关联流程。
4. 客户报告 JSON 快照禁止出现银行、产品、渠道、准入和内部建议字段。
5. 工作台卡片数字与跳转后列表总数一致。

### 9.2 文档不是唯一真源

旧规划仍写“外出事前审批”；菜单规划说部分能力合并为页内 Tab，代码却又拆成独立路由；部分进度文档宣称真实短信/OCR 已完成，而代码仍存在 mock 或未发现完整真实实现。

建议建立一个可执行的决策记录：每项只保留“最终决策、日期、负责人、影响接口、验收用例”。后续需求变更先改决策记录和测试，再改代码。

### 9.3 工作区改动范围过大

审查时工作区约有 60 余个已修改或未跟踪文件，覆盖登录、Nacos、权限、菜单、报告、小程序、数据库脚本。即使功能都正确，也难以独立回滚、定位白屏或审查安全影响。

提交必须按主题拆分：认证与配置、权限与菜单、预约与外出、报告隔离、UI 优化。每个提交只带对应脚本和测试，不混入无关文件。

## 十二、最终验收门槛

系统达到可试运营标准必须同时满足：P0 风险为零；客户接口无法获得任何内部产品/渠道/准入字段；无 token 直连业务服务失败；顾问、经理、老板、运营、超管、渠道六类权限矩阵通过；预约与外出状态在 Web、小程序、H5 文案一致；首页统计可下钻且数字一致。

当前最值得先做的是补齐权限/密钥安全和预约确认语义；外出状态机已按最终口径保留审批、照片和位置硬门槛。
