## 问题 1：日期筛选框与数据列不匹配、不美观

**根因**（已定位）
- 页面组件：`loan-web/src/views/service/ServiceOperations.vue`（员工外出 / 客户预约 / 工作拜访记录共用同一组件，由 `route.meta.serviceView` 切换 tab）。
- 公共组件 `AppDateTime.vue:56-58`：`width` 缺省时回落为 `100%`，在 flex 筛选条里会撑满整行——这是历史遗留的根因。
- Element Plus 的 `daterange` 默认宽 350px，远大于同排 `el-select`（150px）与表格列宽（110~220px），视觉失衡。
- `ServiceOperations.vue:951-954` 虽然传了 `width="280px"`，但 `.scope-toolbar` 为 `flex-wrap:wrap` 且未约束 `flex-shrink:0`，小屏/长标签时仍会被挤压或拉伸。

**修复方案（根因级，覆盖所有受影响页面）**
1. `AppDateTime.vue`：缺省宽度由 `100%` 改为固定 `260px`；daterange/datetime range 外层加 `flex-shrink:0`；删除误导性的 min-width 叠加。
2. 统一筛选条规格（写入共享样式）：下拉 150px / 日期 260px / 输入框 200px / 按钮 auto，`gap: 8px`，与表格首列对齐。
3. 受影响页面清单（同写法一并修复）：`ServiceOperations.vue`、`approval/ApprovalCenter.vue`、`order/OrderList.vue`、`audit/AuditCenter.vue`、`client/ClientProfile.vue`、`product/ProductList.vue`。

## 问题 2：新用户标签判定 + 标签天数「0 / 空」语义

**现状与根因**
- 标签存储：`t_client_profile.customer_tag`（`NEW/INTENTION/POTENTIAL/NO_ANSWER/NO_NEED`）。
- 「新用户 = NEW」是**兜底标签**：`LeadService.customerTagOf()` 在无任何标签/跟进时最终 `return "NEW"`，线索转正建档时写入（`LeadService.java:158`）。
- **为什么你从没见过**：`ClientProfile.vue:730-738` 顶部统计分段 `customerTagSegmentSpecs` 不含 NEW，列表行内标签列虽有映射（`NEW:'新用户'`）但容易被忽略 → 展示缺口，不是没打标。
- **0/空语义错误**（核心 bug）：
  - 前端 `ResourcePoolConfig.vue:153` `saveRecycle` **只提交 >0 的项**，0 根本到不了后端；`:121` 把 ≤0 归 0。
  - 后端 `ResourcePoolConfigService.parseStatusDays:111-119` `if (days > 0)` **≤0 直接丢弃**。
  - 最终 `ClientAllocationService.recycleDays:924-930` + `:846-848` `days <= 0 → continue`（不回收）。
  - 另有硬编码：`DEAL/SIGNED/NO_NEED` 直接 `return 0`（永不回收）。
  - 结论：当前 **0 与「未配置」完全同义 = 不回收**，与预期相悖。

**修复方案（按你定的语义）**
- 语义矩阵：**显式配 0 → 0 天生效（当天即回收）；留空 → 不限制（该标签不参与回收）**。
- 前端：允许输入 0 并提交；留空 = 清除该段配置；文案同步改为「留空=不回收该标签，0=当天回收」。
- 后端：`parseStatusDays` 保留 0 项（`days != null` 即存）；`recycleDays`：map 无此标签（null）→ 不回收；days≥0 → 按 days 判定。
- 删除 `DEAL/SIGNED/NO_NEED` 硬编码 return 0，改由「留空」表达永不回收。
- ⚠️ 数据风险提示：现有「已回收 0」配置在新语义下会变成**当天回收**，需评估是否把存量 0 迁移为空。
- 展示补齐：统计分段加入 NEW（新用户），与列表标签列一致。

## 问题 3：有权限却被判只读

**根因**（两个嫌疑，需确认其一）
1. **角色白名单不一致**：页面/接口白名单只有 `DEPT_MANAGER/BOSS/SUPER_ADMIN/SUPER`（`ResourcePoolConfig.vue:83` 与 `ResourcePoolController.requirePoolManager:141-146`），**不含 OPERATOR**；但菜单 SQL（`migrate-resource-pool-per-pool-recycle-2026-10-19.sql:65-69`）把该页面授权给了 OPERATOR → 运营能进页面却永远只读。而 `ApiPermissionService.java:67-68` 又含 OPERATOR——三处名单打架。
2. **截图与当前源码不一致**：截图上是「仅部门管理员…(只读)」，当前源码文案已是「仅部门经理、老板、超级管理员…保存规则」；`loan-web/dist` 里搜不到该页面 → 疑似你访问的是**未重新构建的旧包**（或 vite dev 未热更新到新代码）。

**修复方案**
1. 权限判定改为**后端单一真源**：列表接口返回 `canManage`（按角色白名单+池归属计算），前端不再本地判角色。
2. 统一三处名单（是否给 OPERATOR 开写权限由你定，默认建议：OPERATOR 只读，名单从菜单授权里收敛）。
3. 确认访问方式：若走 dist/nginx 需重新构建；若 vite dev 请硬刷新。

## 问题 4：顶部「自动回收 30 天」与每池独立配置重复

**根因**
- 你红框的那一行**不是全局配置**，是「创建资源池」表单：`ResourcePoolConfig.vue:10-24`（名称/类型/部门/说明 + 自动回收开关 + 默认 30 天 + 创建按钮），30 只是新池预填默认值——但视觉上像全局配置，误导。
- 真正的全局兜底是遗留表 `t_client_recycle_config(GLOBAL)`，`ResourcePoolConfigService.doResolve:50-68` 仍把它当兜底：优先级 **团队池 > 公司池 > 遗留 GLOBAL**，形成双重配置源。

**修复方案（二选一）**
- A（推荐）：把创建表单收进「创建资源池」按钮弹窗，顶部只留标题+说明；同时**移除 doResolve 的遗留 GLOBAL 兜底**（查不到池 = 不回收，单一配置源）。
- B：保留现状，仅把该行标注为「新资源池默认值」，遗留 GLOBAL 保留但页面加说明。

## 问题 6：编辑客户档案缺报告初筛字段

**根因**
- 客户主表 `t_client_profile` 企业字段**只有** `enterpriseName`、`creditCode`，弹窗（`ClientProfile.vue:193-232`）自然只有这两项。
- 报告初筛真正消费的企业条件字段在规则目录 `engine/catalog/RuleCatalog.java:51-91` 与 `StepConditionEvaluator.java:64-72` 白名单：`region、industry、establish_years、annual_tax、annual_invoice、tax_grade、debt_ratio、invoice_continuity、tax_continuity、biz_status、registered_capital、social_count`。
- 其中一部分已有落库点：`t_lead_ent_ext`（industry/foundYears/taxLevel/annualTaxAmount/annualInvoiceAmount）与 `t_client_business_fact`（field_code/field_value 键值对，规则引擎事实源）。

**修复方案（推荐 c）**
- 弹窗「企业信息」区块补齐字段：行业、成立年限、注册资本、经营状态、地区、纳税等级、年纳税额、年开票额、社保人数。
- 落库三选一：
  - a) `t_client_profile` 加列 —— 主表膨胀，不推荐；
  - b) 写 `t_lead_ent_ext` —— 语义是「线索企业扩展」，客户档案复用别扭；
  - c) **推荐**：统一写 `t_client_business_fact` 键值对（规则引擎直接可取），弹窗保存时 upsert，回显时按 field_code 拉取。
