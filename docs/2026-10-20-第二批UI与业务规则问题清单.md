## 根因 A：弹窗内下拉浮层的统一策略（覆盖 #1 / #4）

**现象**：下拉候选被弹窗边界裁掉；弹窗内容滚动时，下拉面板位置错乱甚至折叠消失；选项多时列表直接溢出弹窗。

**代码证据**：

- `LeadPool.vue:204`、`:228` 显式写了 `:teleported="false"`
- `styles/index.css:1302-1317` 配套加了 `.el-dialog .dialog-select-popper { max-width: 100% }`、`__wrap { max-height: 190px }`
- `ClientLookup.vue:35` 反过来没写 teleport，但没限制列表高度、没锁下拉宽度，50 条长 label 直接把面板撑出弹窗

也就是说：**同一种控件在项目里存在两套互相矛盾的实现**，一套强行塞进弹窗（被裁），一套放出去（溢出）。这就是问题反复出现的根源。

**为什么 `teleported=false` 是错的**：
popper 渲染进 `.el-dialog__body` 后，受 body 的 `overflow` 约束 → 超出即被裁；同时 popper 的位置由触发元素算一次绝对定位，body 内部滚动时不重算 → 表现为"随上下滑动折叠/错位"。

**方案（对齐 Element Plus / Ant Design 主流行为，一次收口）**：

1. 新增 `components/DialogSelect.vue`，内部固定：
   - `teleported` 默认 **true**（浮层挂 body，不受弹窗 overflow 裁剪）
   - `fit-input-width`（下拉宽度 = 触发框宽度，不撑破布局）
   - `popper-class="loan-dialog-select-popper"`，CSS 统一 `max-height: 240px` + 内部 `overflow-y: auto`（**列表自己滚，输入框和弹窗不动**）
   - `popper-options`: `flip` + `preventOverflow`，保证不出视口、不压住输入框
   - `remote` + `:loading` + 防抖内置，避免每处各写一遍
2. 全站弹窗内 select / 日期 / 级联统一改用 `DialogSelect`；删除 `:teleported="false"` 与 `.dialog-select-popper` 的旧样式（**只保留一处定义**）
3. 长 label（如「姓名（角色 · 部门）」）改两行式：主行姓名、副行灰色角色·部门，行高固定 44px，避免横向撑爆

**验收标准**：任选一个弹窗，输入关键字出候选 ≥30 条 → 候选列表在弹窗可视范围内、列表内部可滚动、输入框位置不动、弹窗自身滚动时候选不错位。

## 根因 B：日期控件默认宽度（覆盖 #8，并回答"什么时候能全局统一"）

**先说结论**：第一批把 3 个日期组件收敛成 `AppDateTime` 是对的，但**收口没收在默认值上**。`AppDateTime.vue:62-65` 里：

```js
if (props.width === '' || props.width == null) return '100%';
```

只要某一处忘传 `width`，就一定铺满。所以"统一"永远是靠人记性维持的，漏一处复发一处 —— 这就是 #8 反复的原因。

**#8 的现场矛盾**：`ServiceOperations.vue:25` 已写 `width="280px"`，style 段还有 `.scope-toolbar :deep(.el-date-editor.el-range-editor){width:280px;min-width:280px}`，两层约束都在，截图却仍铺满。必须实测才能定性，候选原因按可能性排序：

1. 浏览器加载的是旧 chunk（HMR 未生效 / 强缓存）—— 自测环境高频；
2. `el-date-editor` 在 flex 容器中被 `flex-grow` 拉伸（inline width 会被 flex 拉伸覆盖）；
3. 截图中铺满的其实是 `el-range-editor` 内部的 `el-range-input` 分配空间，外层卡片被别的规则撑开。

**验证步骤（修复前必做，不许再猜）**：
在出问题的日期框上右键 → 检查 → 看 computed 的 `width` 与 `flex`：

- `width` 是 280px 但仍占满 → 是 flex 拉伸（原因 2）
- `width` 显示 700+ → 样式没命中（原因 1）

**方案（根因级）**：

1. `AppDateTime` 默认宽度按 type 定死，不再回落 100%：
   `date/month/year → 180px`、`daterange → 260px`、`datetimerange → 360px`
2. 仅**表单内**需要铺满时显式传 `width="100%"`（el-form-item 场景约 6 处，逐个补）
3. 组件根元素加 `flex: 0 0 auto`，从物理上拒绝被 flex 拉伸
4. 删除 `index.css:242-245` 的全局 `.el-date-editor.el-range-editor{width:260px}`（与组件内联样式重复、互相打架），统一由组件接管

**验收标准**：全站搜 `AppDateTime`，任何一处不传 `width` 时视觉上都不铺满；筛选条内日期宽度 = 260/360px 固定。

### #5 强制转移确认后提示「系统错误」

- **调用链**：`ClientLookup.vue:130` `assignClient()` → `POST /api/admin/client/{code}/assign` → `ClientAllocationService.directAssign()`。
- **后端会抛的业务异常（都在代码里）**：
  | 后端 message | 触发条件 |
  |---|---|
  | 跨团队客户不可直接分配，需提交申请并由老板审批 | 部门经理操作，目标/原归属与自己不同部门 |
  | 目标归属人不存在或不可用（仅顾问/团队管理者） | 目标工号查不到或非在职 |
  | 客户归属已发生变化，请刷新后重试 | 乐观更新 `changed != 1` |
  | 仅部门经理、运营、老板或超级管理员可直接指定客户归属人 | 角色不足 |
- **前端问题**：`onForceTransferConfirm` 的 catch 用 `String(e.message).includes('跨团队')` 做分支，**靠中文文案匹配**。文案一改（或被全局异常包装成「系统错误」）就匹配失败，落到静默兜底 → 用户看到的就是「系统错误」四个字，无任何可操作信息。
- **方案**：
  1. 后端所有业务异常返回明确 `code`（如 `CLIENT_CROSS_TEAM`），前端按 **code** 分支，禁止匹配中文；
  2. 全局异常兜底不得吞掉业务 message；
  3. 「系统错误」这类兜底文案必须带上 `traceId`，便于定位。

### #6 申请转移报错 + 转移目标选择规则（业务结论，已确认）

**业务规则（用户确认，作为后续实现与验收依据）**：

1. **申请转移（跨团队）**：
   - 第一步：选择目标团队，**只能选非本团队**（本团队不出现在选项里）；
   - 第二步：选择该团队的目标员工（候选随所选团队联动）；
   - 提交后走审批：目标团队负责人初审 → 老板终审。
2. **强制转移（本团队直接生效）**：
   - 目标人选 = **本团队在职成员，排除原归属人**；
   - 提交即生效，不生成审批单（保持 D39 现状）。

**现状与规则的偏差（这就是报错根因之一）**：
`ClientLookup.vue:80` 调 `claimUnassignedClient(clientCode)` 时**不传目标人**；后端 `ClientController:89` 把 `user.getUserNo()` 当作 `targetStaffCode` 传给 `applyTransfer`。而 `applyTransfer` 里走的是 `requireActiveAdviser(targetStaffCode)` —— **userNo ≠ staffCode** 时必然查不到人，直接抛「目标归属人不存在或不可用」。语义上也错：申请转移传的应该是「我申请把客户转给谁」，不是「我自己」。

**方案**：
- 前端：新增「申请转移」弹窗 = 目标团队（非本团队）+ 目标员工（联动）两段式；
- 后端：`POST /api/admin/client/{code}/claim` 增加可选 `body.targetStaffCode`，缺省时才回落申请人本人；同时把 `userNo → staffCode` 的映射收敛掉，禁止再拿 userNo 顶 staffCode；
- 目标员工校验：必须在目标团队、必须在职、非原归属人。
