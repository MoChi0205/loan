## 4. 核心设计

### 4.1 两条事件流 + 一张主干时间轴

事实表管状态（可增删改），事件表管时间轴（append-only），分析层只读。骨架见对话中的架构图。

```
采集层（D-1/D-3/D-5 决定来源）
  部门经理 Web 代录  ｜  顾问小程序确认/代约/跟进  ｜  客户 H5 自助预约·签到
        ↓ 写事实 + 同事务追加事件
事实层（管状态）
  t_client_appointment   预约（状态机）
  t_staff_field_record   员工外勤（状态机 + 审核）
  t_service_follow       客户跟踪记录（激活死表）
  t_service_order        服务工单（已有）
        ↓ 同事务 append-only
事件层（管时间轴/回放）
  t_customer_track_event
        ↓ 聚合（不改主链路）
分析层
  客户画像 ｜ 回放时间轴（员工/客户/渠道三视角）｜ 数据分析看板
```

**为什么独立事件表**：回放要「一个客户的全过程按时间排一列」。若每次 join 事实表 + 日志表，SQL 失控、口径漂移、每加一种事件都要改查询。独立事件表 = 一次写入、一处口径、任意扩类型。

**一致性**：事实写入与事件追加必须同事务；事件表 append-only，不提供 update/delete 接口（合规留痕）。

### 4.2 员工外勤状态机（D-1 + D-6 + D-7 的直接结果）—— 2026-09-21 已落地

```
员工本人提交申请（不允许他人代录）
      ↓
  PENDING_REVIEW 待审核 ──驳回──→ REJECTED 已驳回 ──修改重提──→ PENDING_REVIEW
      ↓ 主管审核通过
   READY 待出发 ──出发打卡（照片+定位）──→ IN_PROGRESS 外出中 ──返回打卡（照片+定位）──→ COMPLETED
                                    └────────── CANCELLED（非终态均可）──────────┘
```

| 环节 | 谁做 | 硬约束 |
|---|---|---|
| 提交申请 | **预约的主服务顾问本人** | 他人（含管理角色）一律 403；一个预约只能有一条外出记录 |
| 审核 | 部门经理（本部门）/ 老板 / 运营 / 超管 | **禁止自审**；部门经理只能审本部门；驳回原因必填 |
| 出发·返回打卡 | 申请人本人 | **必须同时有现场照片 + 单点定位**；先 `PENDING_REVIEW` 未通过时打卡不成立 |
| 照片预览 | 本人，或有审核权者 | 走受控接口，不回存储路径 |

**关于「实时看谁在外面」**（原 A1/A2/A3 讨论的落点）：
现在是**事前审批**模式——`READY`（已批待出发）与 `IN_PROGRESS`（外出中）是两个不同状态，所以
「坐席外出名单」既能看**待办**（谁的申请还没审）、也能看**在外中**（已出发未返回），比纯事后台账更有用。
若后续需要「人是不是真的在现场」，已有单点定位+照片双凭证，不必再引打卡设备。

### 4.3 到店记录的三源合并（D-5 的直接结果）

三个来源写进来的都是「同一个客户、同一次到店」，必须去重，否则名单会重复计数。

**策略（提议）**：以 `t_client_appointment` 为**唯一主记录**，三个来源作为**到店证据**写入事件表 + `arrived_source`：

| 来源 | 产生方式 | 可信度 |
|---|---|---|
| `WEB_FRONT` | 部门经理/运营在 Web 代录 | 中（事后补录） |
| `ADVISER_CONFIRM` | 接待顾问在小程序点「确认到店」 | 高（人在现场） |
| `CUSTOMER_CHECKIN` | 客户 H5/小程序扫码或点击签到 | 高（客户自己产生） |

**合并规则**：同一次预约内，`arrived_at` 取**最早**一条证据的时间；`arrived_source` 保留**全部**来源列表（不覆盖，便于追溯与争议处理）；无预约的临时到店 → 自动生成一条"无预约到店"的 appointment（`appoint_type=ON_SITE`、`initiator=CUSTOMER`）。

### 4.4 数据模型

**新增 4 张 + 1 组标签**

**① `t_customer_track_event`（主干事件表）**

| 字段 | 说明 |
|---|---|
| `event_no` | 业务编码 |
| `client_code` / `lead_no` | 客户编码 / 线索编码（线索阶段事件只有后者） |
| `event_type` | 事件类型（见 4.5） |
| `occurred_at` | 业务发生时间（≠ 写入时间） |
| `actor_type` / `actor_no` / `actor_name` | 触发方（STAFF / CUSTOMER / CHANNEL / SYSTEM） |
| `source_table` / `source_id` | 反查事实表，保证可追溯 |
| `payload` | json，事件细节（不复制敏感明文） |
| `visibility` | `INTERNAL` / `CUSTOMER` / `CHANNEL` —— 决定能否出现在对客回放 |
| `created_at` | 写入时间 |

索引：`(client_code, occurred_at)`、`(lead_no, occurred_at)`、`(event_type, occurred_at)`、`(actor_no, occurred_at)`。后两个直接支撑「每日来访名单」与「顾问活跃度」。

**② `t_client_appointment`（预约 / 到店主记录）**

`appointment_no` / `customer_group` / `client_code` / `lead_no` / `appoint_type`（`ON_SITE` 到店 / `VISIT` 上门 / `ONLINE` 线上）/ `appoint_start_at` / `appoint_end_at` / `initiator_type`（`STAFF` 代约 / `CUSTOMER` 自助）/ `initiator_no` / `receiver_staff_code`（接待顾问）/ `status`（`PENDING` 待确认 / `CONFIRMED` 已确认 / `ARRIVED` 已到店 / `CANCELLED` 已取消 / `NO_SHOW` 未到店）/ `arrived_at` / `arrived_source`（三源列表）/ `cancel_reason` / `remark` + 标准留痕字段。

**③ `t_staff_field_record`（员工外勤，带审核）**

`record_no` / `staff_code` / `staff_name` / `dept_code` / `record_type`（`OUT` 外出 / `VISIT` 上门拜访 / `ON_SITE` 驻点）/ `reason`（事由）/ `client_code`、`lead_no` / `plan_start_at` / `plan_end_at` / `actual_start_at` / `actual_end_at` / `status`（`PENDING_REVIEW` / `PASSED` / `REJECTED`）/ `recorder_staff_code`（**代录人**，D-1 关键字段）/ `reviewer_staff_code` / `reviewed_at` / `review_remark` + 标准留痕字段。

**④ `t_client_tag` + `t_client_tag_rel`（画像标签）**

`t_client_tag`：`tag_code` / `tag_name` / `tag_group`（基础属性/经营/行为/价值/风险）/ `tag_type`（`AUTO` 规则型 / `MANUAL` 人工）/ `value_type` / `status` / `sort`。
`t_client_tag_rel`：`client_code` / `tag_code` / `tag_value` / `source` / `operator` / `valid_until`（撤销用失效时间，**不删行**）。

**改造 1 张表：激活 `t_service_follow`（向后兼容）**
- `order_id` → **可空**；新增 `client_profile_code`、`lead_no`（解决「客户来面谈但还没工单」无处记录）
- `channel_type` 扩展：保留 `VISIT/PHONE/WECOM/MEETING`，新增 `ON_SITE_VISIT`（客户到访）、`OUT_VISIT`（员工上门）
- 新增 `follow_result`（跟进结果，用于漏斗）、`visible_to_customer`（该条是否对客可见，默认 0）
- 该表**零代码引用**，改造风险极低；迁移脚本 + `db/loan-db-schema.sql` 双向同步（项目惯例）

## 5. 画像与数据分析

### 5.1 画像四层（**仅系统内数据**，D-4）

| 层 | 内容 | 数据来源 | 谁可见 |
|---|---|---|---|
| L1 基础属性 | 客群、企业名、行业、地区、VIP 与到期、来源、注册时间、实名状态 | `t_client_profile` / 扩展表 | 客户自己 + 员工 |
| L2 经营画像 | 营收/纳税/负债/征信/流水区间、经营年限、资产结构 | `t_client_business_fact`（已有提取层） | 员工；客户看自己的 |
| L3 行为画像 | 预约次数、到店次数、最近来访、跟进频次、响应时长、材料补交次数、报告查看次数 | **本方案新增的事件表** | **仅内部** |
| L4 价值/风险 | 成交额、服务单数、成交周期、闲置天数、超期未跟进、多次未到店 | 服务单 + 事件表 + `last_followed_at` | **仅内部** |

**AUTO 标签只做规则型**（因 D-4 排除了模型评分），例如：`到店≥3次`、`30天未跟进`、`有预约未到店`、`VIP即将到期`、`已成交`、`材料缺口未补`。不做「高意向/流失风险」这类需要模型或外部数据的评分标签。

### 5.2 数据分析（口径先定死，避免各页各算）

| 看板 | 核心指标 |
|---|---|
| 客户漏斗 | 录入 → 审核通过 → 认领/分配 → **预约** → **到店** → 提交材料 → 匹配 → 报告 → 服务单 → 成交（每层转化率 + 平均停留时长） |
| 到店分析 | 预约量、到店率、未到店率（`NO_SHOW`）、平均到店时长、按顾问/部门排行、三源占比 |
| 跟进健康度 | 超期未跟进数（`last_followed_at` 超阈值）、平均跟进间隔、`next_follow_time` 逾期数 |
| 顾问活跃度 | 跟进条数、到店接待数、外出次数与时长、匹配执行数、成交数 |
| 坐席外出 | 外出次数/时长、按事由分布、按部门分布、**审核及时率与驳回率**（D-6 新增） |
| 趋势 | 上述指标按日/周/月趋势（对齐现有 `report/TrendAnalysis.vue` 呈现方式） |

### 5.3 回放（客户时间轴）

同一份事件表，**一个接口三种视角**，靠 `visibility` + 权限过滤：

- **员工回放**（Web + 员工小程序）：全事件，可按类型过滤，可跳源头单据
- **客户回放**（H5/小程序）：仅 `CUSTOMER` 事件，对客措辞，**无单号、无内部备注**
- **渠道回放**（Web 只读，D50）：仅「本人录入客户」范围内的公开事件

## 7. 权限与合规（硬约束）

1. **外勤记录 = 人事数据**：本人可见（只读）、部门经理可见本部门、老板/运营/超管全量；**渠道不可见、不进入客户回放**。
2. **提交人留痕**：外勤只由本人提交（`staff_code` + `created_by`）；审核留 `reviewer_staff_code` / `reviewer_name` / `reviewed_at` / `review_remark`。**禁止自审**在服务层强制。
3. **客户端零业务单号**（D68）：客户回放/我的预约只展示事项、时间、状态。
4. **合规表述**：对外「资金」不用「贷款/融资」；「审核」不用「审批」。
5. **打卡采集范围（2026-09-21 修订 D-7）**：出发/返回各采**一次**单点定位（经纬度 + 精度 + 位置文本，AES 密文落库）+ **一张现场照片**；
   **不采集连续轨迹**，不做后台定位；定位与照片仅用于外勤核实与审核，最小授权读取（本人 + 有审核权者）。
6. **敏感查看**：画像页展示身份证/手机号走既有 `t_sensitive_view_log` 日限额与授权校验。
7. **留痕不可删**：事件表 append-only；标签撤销用失效时间。
8. **接口权限三件套**（D76/D79）：① 新 Controller 启动期自动登记 apiKey；② 员工角色默认矩阵补 apiKey；③ 渠道需精确 method+path 白名单，**不得放宽 `mini:` 前缀**。
9. **数据可见范围下沉到 SQL**：部门经理的"本部门"过滤必须在查询层实现（参照 15-规则的团队范围写法），不能靠前端筛。
10. **跟进记录唯一真源**（D-8）：一律写 `t_client_follow_record`；`t_service_follow` 已标记废弃，禁止新增引用。

## 12. 验收口径（先定，避免返工）

- **代录效率**：一条外勤登记 ≤ 1 分钟完成；批量代录（多人同日）支持一次提交
- **审核闭环**：待审核列表可分部门筛；驳回可改后重提；**未通过绝不进名单**（自动化断言）
- **到店去重**：同一预约三个来源都产生时，名单只计 1 次，`arrived_at` 取最早（断言）
- **回放可用性**：任一客户时间轴单请求返回，首屏 < 1s（分页 + 索引）
- **对客合规**：客户回放返回体**零单号、零内部备注、零人事信息**（断言）
- **权限不越界**：部门经理只能看本部门外勤；渠道调用内部接口 403；**部门经理不能自审自己的记录**（断言）
