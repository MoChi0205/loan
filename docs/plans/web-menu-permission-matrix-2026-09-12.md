# Web 菜单与权限矩阵（2026-09-12）

## 设计依据

本方案借鉴 `tse/docs2` 的做法：角色矩阵是唯一业务真源，菜单种子和文档由矩阵派生，发布前校验“菜单 → 路由 → 首屏接口 → Gateway → Controller → 数据范围”完整链路。

## 当前项目菜单责任边界

| 业务域 | 菜单 | 责任边界 |
|---|---|---|
| 工作台 | 工作台 | 当前角色待办、指标、消息，不承载管理配置 |
| 客户经营 | 线索管理、客户档案、团队公海、材料识别 | 线索新增/认领、公海回收分配、客户基础档案、材料上传识别；团队公海仅部门经理可见 |
| 匹配与规则 | 初筛任务、规则库、规则集、策略方案、执行计划 | 智能匹配和准入规则；不直接承担客户归属审批 |
| 服务与审核 | 服务工单、审批中心 | 工单处理与审批；顾问只有申请权限，不能显示审批操作 |
| 运营与激励 | 短信服务、奖励发放、奖励规则、审计日志 | 运营内容、奖励结算、操作审计；短信和报告模板发布需老板/超级管理员审批 |
| 数据与报表 | 经营概览、趋势分析、初筛报告、报告模板 | 报表查询、客户报告、模板管理；报告标题只显示客户与日期 |
| 产品与渠道 | 产品库、渠道档案、渠道准入、渠道名单、风控名单 | 产品/渠道业务；渠道提交内容进入审批，不直接进入生效库 |
| 系统管理 | 组织权限、系统配置、调试中心 | 仅系统配置角色；老板是业务全量但不是系统配置管理员，调试中心受环境开关控制 |

## 角色菜单口径

| 角色 | 菜单口径 | 数据范围与关键限制 |
|---|---|---|
| CUSTOMER | 不进入 Web 管理端 | 仅小程序本人客户、报告、工单 |
| CHANNEL | 工作台、线索管理、客户档案、产品库、初筛报告 | 仅本人录入；可新增线索/产品，不能匹配、分配、审批 |
| ADVISER | 工作台、线索管理、客户档案、团队公海、材料识别、初筛任务、服务工单、经营概览 | 本人客户；可认领公司公海/本团队公海、释放本人客户、提交审批；无审批按钮 |
| DEPT_MANAGER | 顾问菜单 + 团队已分配客户、团队公海、审批、产品/规则、报告、运营查询 | “我的客户”仅本人归属；“团队已分配客户”=本部门成员名下已分配客户；“团队公海”=本部门回收客户；可直接分配/回收本团队客户，跨团队操作须老板审批 |
| OPERATOR | 业务全量 + 运营与审批 + 系统管理（不含调试） | 公司范围；短信/报告模板发布必须老板/超级管理员审批 |
| BOSS | 业务全量 + 审批 | 公司全量；可审批跨团队和运营内容；不开放组织配置写入口 |
| SUPER_ADMIN/SUPER | 全量业务与系统管理 | 全平台；可维护菜单、角色、接口权限和调试开关 |

## 必须同步的四层契约

1. `t_menu`: `path` 唯一、`parent_id` 表达业务域、`permission_code` 表达页面/按钮权限。
2. `t_role_permission`: 角色与菜单/按钮绑定；不得依赖前端角色常量兜底放权。
3. `t_api_permission` / `t_role_api`: Gateway 接口登记、端类型和角色授权；菜单可见不等于接口可调用。
4. 前端 `router`、`Layout.vue`、`v-permission`: 只做展示和路由映射，不能扩大服务端权限。

## 发布校验

- 每个菜单必须能映射到一个路由或合法父节点。
- 每个角色菜单都要检查页面首屏 API 是否在 Gateway 登记并授权。
- 父菜单无子菜单时不展示；无权限路由直接 403，不能加载页面数据。
- 顾问、渠道的授权使用精确接口键，禁止用模块前缀放行。
- 修改菜单后必须同步矩阵文档、DDL/种子、角色权限、接口权限和回归用例。

## 借鉴 TSE 的工程化改进

- 增加机器可读矩阵，后续由脚本生成 SQL、文档和角色回归用例。
- 菜单文档按业务域拆分，页面、Controller、API、表结构在同一条记录中维护。
- 每次菜单迁移输出角色计数和“菜单路径—路由路径”差异，避免静态菜单与数据库漂移。
