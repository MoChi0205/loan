# Web 端菜单重构规划（产品视角）

> 日期：2026-09-22 ｜ 范围：loan-web 管理端侧边栏菜单
> 目标：层级清晰、语义无歧义、功能面向角色清晰、描述清晰
> 现状真源：`loan-web/src/layout/Layout.vue#BASE_MENU_GROUPS`（前端静态）+ `t_menu`/`t_role_permission`（后端动态授权）

---

## 一、现状问题诊断

### 1. 分组按「技术模块」而非「业务域」，语义交叉
| 现状分组 | 问题 |
|---------|------|
| 客户经营 | 「客户服务」被拆到了别组，客户全生命周期不完整 |
| 匹配与规则 | 「初筛任务」是操作、「规则库/执行计划/策略方案」是配置，混为一组 |
| 服务与审核 | 「客户服务」「服务工单」「我的审批」三个不同性质（交付/工单/审批）挤在一起 |
| 运营与激励 | 「短信服务」「奖励」「审计日志」分属触达/激励/合规，非同类 |
| 产品与渠道 | 「风控名单」是全局合规，放这里语义不符 |

### 2. 命名歧义（用户一眼看不懂）
| 现状命名 | 路径 | 歧义点 |
|---------|------|--------|
| 用户查询 | /client-lookup | 「用户」指客户还是系统账号？实为「客户检索」 |
| 规则库 vs 规则集 | /rule-template vs /rule | 一个「模板」一个「实例」，命名无层级感、顺序反直觉 |
| 策略方案 | /strategy-template | 菜单叫「方案」，实际指向「策略模板」列表，名实不符 |
| 客户服务 | /service-operations | 与「服务工单」语义重叠，实为「来访/外出/跟进」聚合 |
| 我的审批 | /approval | 与小程序「审批中心」命名不一致 |

### 3. 同一对象被割裂在两个分组
- 「初筛任务」（/screening）在「匹配与规则」，「初筛报告」（/report/screening）在「数据与报表」——同一业务对象（初筛）分家，用户找不到对应关系。
- 「奖励发放」与「奖励规则」拆成两个菜单，同属「推荐有礼」一件事。

### 4. 角色面向不清晰
- 顾问 / 部门经理 / 老板 / 运营 / 超管看到**同一套菜单**，仅靠 `roles` 字段隐藏少数项，没有体现「谁该看什么」的分层。
- 渠道是外部合作方，却和内部员工共用菜单结构（只靠标题替换），职责边界不清晰。

---

## 二、设计原则

1. **按业务域 + 用户旅程分组**：获客 → 建档 → 匹配 → 交付 → 激励 → 分析，而非按技术模块。
2. **命名 = 业务对象 + 动作**：如「线索管理」「客户档案」「匹配任务」「服务工单」，不用技术词（OCR、规则集）。
3. **面向角色**：每个菜单明确「谁用」；同一组内按角色可见性分层。
4. **层级 ≤ 3 级**：一级导航分组 → 二级菜单页面 → 页面内 Tab/区块。

## 三、新菜单树（核心方案）

> 分组名 = 一级导航；`→` 下为二级菜单。每条标注【定位】【面向角色】【描述】。

### ① 工作台（置顶，无分组）
- **工作台** ｜ 定位：登录首页 ｜ 角色：全部
  - 描述：聚合待办（待审批 / 待跟进 / 待匹配）与快捷入口，一键进入高频操作。

### ② 客户中心（客户全生命周期）
- **线索管理** ｜ 定位：获客阶段 ｜ 角色：顾问 / 部门经理 / 老板 / 运营 / 超管
  - 描述：线索录入、查询、公海认领、释放、归属分配。
- **客户档案** ｜ 定位：建档后的客户经营 ｜ 角色：顾问及以上
  - 描述：客户详情、归属顾问、画像、生命周期事件、跟进历史。
- **客户检索**（原「用户查询」）｜ 定位：统一检索 ｜ 角色：顾问及以上
  - 描述：跨线索/客户按关键词统一检索，消除「用户」歧义。
- **团队公海** ｜ 定位：部门团队客户池 ｜ 角色：**仅部门经理**
  - 描述：本部门成员名下客户视图 + 回收。
- **客户材料**（原「OCR 材料」）｜ 定位：材料管理 ｜ 角色：顾问及以上
  - 描述：客户提交材料的解析、核验与归档。

### ③ 智能匹配（业务核心：匹配 + 诊断）
- **匹配任务**（原「初筛任务」）｜ 定位：发起匹配 ｜ 角色：顾问及以上（渠道除外）
  - 描述：发起智能匹配、查看初筛结果。
- **诊断报告**（原「初筛报告」从报表域移回）｜ 定位：匹配产出 ｜ 角色：顾问及以上（渠道可见本人报告）
  - 描述：经营诊断报告，与「匹配任务」同域，形成闭环。

### ④ 服务交付（服务过程）
- **服务台**（原「客户服务」改名）｜ 定位：服务现场协同 ｜ 角色：顾问及以上
  - 描述：今日来访、员工外出、预约、跟进沟通的统一工作台。
- **服务工单** ｜ 定位：工单流转 ｜ 角色：顾问及以上
  - 描述：服务工单的创建、分派与状态跟踪。

### ⑤ 审批中心（统一审批）
- **审批中心**（原「我的审批」改名统一）｜ 定位：统一审批入口 ｜ 角色：部门经理 / 老板 / 运营 / 超管
  - 描述：待我审批 + 我的申请（Tab 区分），与小程序「审批中心」命名一致。

### ⑥ 营销激励
- **短信服务** ｜ 定位：触达 ｜ 角色：运营及以上（模板需老板终审）
  - 描述：短信模板管理 + 发送。
- **奖励管理**（合并「奖励发放」+「奖励规则」）｜ 定位：推荐有礼 ｜ 角色：运营及以上
  - 描述：推荐有礼的奖励规则配置与发放（同一页面 Tab 区分）。

### ⑦ 经营分析（面向管理角色）
- **经营概览** ｜ 定位：核心指标 ｜ 角色：老板 / 运营 / 超管（顾问 / 部门经理看「实时看板」）
  - 描述：核心经营指标看板。
- **趋势分析** ｜ 定位：趋势 ｜ 角色：管理角色
  - 描述：经营与匹配趋势。
- **报告模板** ｜ 定位：诊断报告模板 ｜ 角色：运营及以上（需老板终审）
  - 描述：诊断报告模板管理。

### ⑧ 产品与规则（供给侧配置）
- **产品库** ｜ 定位：产品管理 ｜ 角色：渠道（我的产品）/ 运营及以上（全量）
  - 描述：贷款产品库管理。
- **渠道管理**（合并「渠道档案 + 渠道准入 + 渠道名单」）｜ 定位：渠道全周期 ｜ 角色：运营及以上（内容终审仅老板/超管）
  - 描述：渠道档案、准入审批、渠道名单（页面内 Tab 区分）。
- **规则模板**（原「规则库」）｜ 定位：匹配规则模板 ｜ 角色：运营 / 老板 / 超管
  - 描述：匹配规则的模板定义。
- **规则实例**（原「规则集」）｜ 定位：规则实例 ｜ 角色：运营 / 老板 / 超管
  - 描述：由模板生成的规则实例，与「模板」形成层级。
- **执行计划** ｜ 定位：准入编排 ｜ 角色：运营 / 老板 / 超管
  - 描述：准入执行计划编排。
- **策略方案** ｜ 定位：策略 ｜ 角色：运营 / 老板 / 超管
  - 描述：策略方案（含模板），明确指向策略列表。

### ⑨ 系统管理（系统级）
- **组织权限** ｜ 定位：组织与权限 ｜ 角色：运营 / 超管
  - 描述：组织架构、角色、菜单、接口权限。
- **审计日志** ｜ 定位：合规 ｜ 角色：运营 / 超管 / 老板
  - 描述：操作审计日志。
- **风控名单**（从「产品与渠道」移入）｜ 定位：风控 ｜ 角色：运营 / 老板 / 超管
  - 描述：黑名单/风控名单管理（全局合规，非渠道专属）。
- **系统配置** ｜ 定位：系统参数 ｜ 角色：运营 / 超管
  - 描述：系统参数配置。
- **调试中心** ｜ 定位：仅开发 ｜ 角色：超管（生产隐藏）
  - 描述：调试工具，仅 dev 环境可见。

## 六、落地注意事项（改菜单必须同步五处）

依据 `01-角色权限模型.md` D53 真值，改菜单不能只改前端：

1. `t_menu` + `t_role_permission`（后端动态授权真值）
2. `t_api_permission` / `t_role_api`（接口权限）
3. 前端路由（`router/index.js`）+ `Layout.vue` 菜单项
4. Controller 角色守卫 + 数据范围
5. `scripts/verify_menu_matrix.py` 校验

**额外提醒**（本次排查发现的后端坑）：`OrgService.buildTree` 对「父菜单存在但角色未授权父菜单」的子菜单会**静默丢弃**。新增子菜单必须同时授权父菜单，否则会出现「SQL 执行了但菜单不显示」。

## 七、分期建议

- **P0（低风险、纯改名/合并）**：命名修正（用户查询→客户检索、客户服务→服务台、我的审批→审批中心、奖励合并、渠道合并、风控移组）。
- **P1（结构调整）**：初筛报告并入智能匹配域、规则库/规则集改模板/实例。
- **P2（可选，需评审）**：是否把「渠道管理」拆回 3 个子菜单、是否新增「风控合规」独立分组。
