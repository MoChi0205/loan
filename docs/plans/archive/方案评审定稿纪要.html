05合作渠道银行用户体系

账号与邀请码运营

  • 开通方式：我司在管理端生成渠道邀请短码发给银行对接人 → 对方凭码自助注册（手机号+验证码+密码+姓名岗位）→ 绑定所属银行渠道
  • 账号数量：不硬性限数，但每个账号都需我司单独生成邀请码——审批制开通，防滥发
  • 角色：单一角色（录入草稿 + 查审核进度 + 收消息），不做对方内部的角色分级
  • 邀请码规则：7 天有效、单次使用（注册成功即作废）、我司可随时作废重发
  • 停用时机：该渠道合作库产品全部到期 或 我司手动停用 → 账号即时失效、登录态踢下线

06渠道产品审核流

① 渠道创建产品（草稿）→ ② 提交审核→ ③ 我司人工审核（48h）→ ④ 通过入全量库→ ⑤ 我司上架合作库（设有效期）→ ⑥ 对客可见·参与匹配

审核规则

  • 新建与变更都走审核：已上线产品修改（利率/门槛调整）→ 生成草稿副本 → 提交 → 我司通过后才替换生效，前后快照入审核工单（t_product_approval）全程可追溯
  • 审核人：走部门审核人配置（t_dept_approver：部门 × 审核类型 × 审核人，第十八轮定稿）——产品审核按部门逐项指定审核人（可多人、可跨部门），未配置默认老板兜底，老板可随时调整
  • 审核时效：48 小时内审完（可配置），超时仪表盘+消息提醒老板；渠道端显示"预计 48 小时内反馈"
  • 审核意见：驳回必填意见（渠道据此修改），通过可选填备注，全部留痕
  • 重复产品：审核时系统自动比对（同渠道同名/同额度区间），命中标红提示，由审核人决定"合并更新"或"驳回沟通"
  • 入库分层：审核通过仅入全量库 t_bank_product（标记来源=渠道自建+所属渠道）；是否上架合作库由我司二次操作并单独设 cooperate_until 有效期——对客可见权始终在我司手里
  • 审核结果通知：通过/驳回均发小程序站内消息 + 短信（驳回附意见摘要）

07规则权限与基础风控双层结构

  • 渠道对规则的权限：渠道用户只填条件资料结构化表单（额度/利率/期限/纳税门槛/开票要求等业务条款），支持上传产品截图/文字 → OCR/AI 提取自动回填表单字段（详见第 22 章，识别仅辅助录入、可编辑后再提交）；规则引擎配置由我司翻译并负责上线校验——规则质量我司兜底，不放开给外部人员
  • 基础风控=全局+产品双层：
    • 全局前置模块：黑名单 / 失信名单 / 欺诈核验 / 区域限制 / 敏感行业禁入——所有产品（不论哪家银行）匹配前必过，命中直接 REJECT；渠道用户不可见、不可改；黑名单（t_blacklist，第十八轮定稿：手机号/身份证/企业统一信用代码/法人多维命中，原因分类留痕）顾问可查询命中情况与新增（提交即全局生效、留痕到人），删除/解禁仅老板可操作，仅我司管理端维护
    • 产品级叠加：我司可给单个产品追加额外风控模块（两层风控）

五方引荐机制

  • 业务引荐（五方均可，仅做归属/公海/计数，不涉及奖励）：我司老板 / 员工顾问 / 渠道银行用户 / VIP 客户 / 受邀客户均可引荐客户；推荐奖励功能仅对受邀用户有效，渠道合作方与公司员工均无此功能
  • 绑定方式：主路径=引荐人专属小程序码/链接（scene 携带引荐码，扫码自动绑定）；兜底=线下口头场景手填「引荐码 + 引荐人姓名」双字段，服务端校验两者匹配才放行
  • 引荐码形式：一对一短码（7 天单次有效，谁邀请谁归属）+ 顾问长期固定码兜底，两者都要
  • 客户归属：我司员工邀请 → 自动归属邀请人（owner_uid）；渠道引荐 → 先进公海，由老板再分发（渠道侧只见"引荐了几人、转化了几人"计数统计，不见客户明细）；受邀用户分享链接邀新 → 绑定推荐关系，被推荐人完成触发动作后进入推荐奖励结算（见下节，仅受邀用户参与）
  • 引荐关系落表：t_invitation（类型/短码/有效期/使用状态/邀请人/引荐人类型 含 CUSTOMER 受邀用户推荐）；企微活码参数同入该表溯源体系；仅 referrer_type=CUSTOMER 的受邀用户推荐关系进入奖励结算，员工/渠道引荐只记归属不产生奖励

客户推荐奖励机制（成交金额驱动 · 我司控制结算）

  • 分享主体（功能边界）：仅受邀用户（受邀注册并完成认证的客户）可分享专属邀请链接；渠道合作方、公司员工无此功能；非受邀用户（含在线付费购买的 VIP）无分享入口、看不到奖励中心——分享与奖励整体仅对受邀用户有效；被推荐人须为新注册用户（手机号去重校验），自邀自（同号/同设备）不产生奖励；受邀用户可继续分享裂变（A邀B → B可再邀C），层级封顶 2 层
  • 奖励形态：现金红包 + 服务权益（VIP 时长续期 / 报告次数）混合，按 t_reward_rule 比例规则自动匹配，全部后台可配不写死
  • 成交金额基数（奖励计算基数）：取自 t_service_order 服务工单进入 DEAL 已成交状态的单子——① CRM 合同金额（咨询服务合同回写自动建单并置 DEAL）＋② 线下成交补录（管理端录入直接建单置 DEAL，必填成交单号/合同号+凭证附件，操作人留痕，奖励单标记「线下补录」）；线上 VIP 支付不计入基数（VIP 是身份/权益，不是成交来源）
  • 自动结算为主 + 后台手动调整兜底：默认按 t_reward_rule 比例自动计算「奖励金额 = 成交金额 × 比例」并冻结快照（成交金额/适用比例/计算过程/规则版本），后续改比例不影响已生成奖励单；后台可手动改写奖励金额（特批兜底：必填调整原因 + 操作人留痕 + 标记「人工调整」+ 调整日志可查）
  • 层级 = 发 1 层 · 存 2 层：金额奖励只发给直接推荐人（第 1 层直推）；推荐关系链仍记录 2 层深度（可追溯/防刷/展示上家），第 2 层间推金额后台预留开关默认关闭，将来可开启；第 3 层自动截断（层级封顶 2 层，合规可控）
  • 结算状态机（我司全程控制）：成交落库 → 自动计算入单 → 待审核（进管理端）→ 通过后自动提现到微信零钱（微信商家转账到零钱，商户号开通转账能力，无需客户操作）/ 已驳回（驳回必填原因）；转账失败自动重试 3 次后转人工处理；客户侧仅查看奖励单状态，无自助提现/改绑入口；异常单可一键作废并关联线索
  • 推荐人奖励中心（小程序，仅受邀用户可见）：奖励明细（成交单号 → 成交金额 → 比例 → 奖励金额 → 状态）+ 历史总金额 / 当月 / 当日（总额含待审核，明细区分状态，另显示已到账合计）+ 推荐客户数 / 成交数；到账以微信零钱通知 + 站内消息触达
  • 可追溯 · 可查账：全链路明细（成交单号 → 成交金额 → 比例快照 → 奖励金额 → 发放状态，逐级可展开核对）；管理端四维查账（成交单/推荐人/时间/状态任意组合）+ 对账单导出；线下补录、人工调整、审核动作留痕到人（操作人+时间）
  • 最终解释权：客户端奖励单底部与管理端默认展示「最终解释权归我司所有，奖励规则以我司后台配置与公示为准，结算金额以成交单与快照为准」
  • 合规红线：奖励话术与微信转账场景备注统一用「推荐奖励 / 专属服务权益」，不出现返现、佣金等金融敏感词；层级封顶 2 层（3 层起涉传销红线）
  • 落表三张：t_reward_rule（奖励规则：比例配置-直推 X% / 间推 Y% 开关 / 基数口径 / 有效期 / 上下限）、t_reward_record（奖励流水：推荐人/层级 1·2 / 关联服务工单号 / 基数金额快照 / 比例快照 / 规则版本 / 状态机 / 人工调整标记与原因 / 结算人 / 时间戳）、t_withdraw_record（提现流水：奖励单/微信转账单号/金额/状态-待转账→转账中→成功/失败/失败原因/重试次数/到账时间/操作人）；成交数据不再重复落表，直接引用服务工单域 t_service_order（见下节）

服务工单与营收统计（业务订单主表）

  • 定位：t_service_order 服务工单 = 我司咨询服务业务订单主表（由原 t_deal_record 成交记录升级），一套数据支撑客户 / 推荐人 / 公司三个视角；与 CRM 履约工单解耦（loan 记业务订单与金额，CRM 跑履约进度）

10报告展示分级与企微转化（核心合规定位）

合规声明基线：报告仅提示预计可通过的银行数与经营报告和银行产品的匹配程度（预计通过概率），不是真正的银行产品通过结果，具体以实际银行审批为准；想查看具体银行产品，需添加咨询服务经理企业微信 1 对 1 详细咨询。客户报告另附多维建议：从纳税/开票/负债/行业等维度给出提升银行审核通过率的可改进方向（建议文案库后台可配，随报告模板版本锁定，话术避免承诺性表述）。

① 概率展示形式 = 档位制（高/中/低）

  • 结果页主展示「匹配程度：高/中/低」，不使用百分比数字——百分比属伪精确（银行审批含人工与政策变量，系统算不出真实通过率），客户拿"78% 为何被拒"投诉时无法举证，且表述接近贷款中介承诺话术、小程序类目审核敏感
  • 档位映射规则后台可配（如：命中 ≥3 个产品且核心维度全过 = 高），随报告模板版本管理，改档位规则不影响历史报告

② 数量颗粒度 = 仅数量，不露产品名

  • 小程序匹配结果页只展示「预计可进件 N 家」，银行名称、产品名称、利率、额度一律不出现在客户端
  • 规则引擎照常计算命中产品明细并全量落审计（t_match_trace / t_match_rule_log）——只是展示层屏蔽；管理端审计中心仍可看全量明细
  • 三态卡片保留：PASS 可进件（绿）/ CONDITION 需补料（橙，列出缺哪些维度）/ REJECT 暂不匹配（灰，附原因摘要）

③ 企微承接 = 混合模式

  • 有归属顾问的客户：展示顾问个人企业微信码
  • 无归属顾问的客户（公海/未分配，第十九轮定稿）：展示兜底顾问池中当前负载最少者的企微码——管理端可配置 1~N 位兜底顾问（与角色无关，普通顾问即可被设为兜底，每人绑定企微二维码/启停/排序），按当前负载最少分配并留痕，可随时更换；原公司客服活码并入兜底池作为可配置项之一
  • 活码带渠道/来源参数（入 t_invitation 溯源体系），添加企微后转化沉淀为公司客户资产（CRM 跟进），不随个人流失
  • 企微引导位（合规摆放）：匹配结果页底部「查看具体产品方案」按钮 · 报告尾页「添加咨询服务经理」· 顾问名片页活码

④ 免责声明双落（每份报告必带）

  • 落点一：报告模板尾页；落点二：匹配结果页页脚
  • 文案基调：「本报告为企业经营状况与银行产品准入条件的匹配程度分析及预计概率，不构成任何银行通过承诺，具体以银行实际审批为准；银行产品详情请添加咨询服务经理企业微信 1 对 1 咨询」
  • 与溯源水印（客户企业名+手机号后四位+生成时间）、数据来源声明、报告权属声明共同构成报告合规四件套

15规则引擎语义

  • 实现参考 mds V2（第二十四轮定稿）：渠道准入规则引擎参考 /Users/admin/IdeaProjects/mds 的 v2 包（mds-service/.../com/xr/dam/mds/v2）——计划→模块→步骤、策略执行器 AND/OR、RuleConditionEvaluator 条件评估器、AdmissionRuleRegistry 注册表、审计 Trace+RuleLog、批量 handleBatch、dryRun 影子执行，参考架构重写为 com.loan 包（不直接拷贝 mds 代码）
  • 规则表达 = 混合模式（参考 mds）：规则 = ruleCode 处理器（Handler 注册表索引）+ 条件表达式（conditionField/conditionOperator/conditionValue 后台可配）；数值/枚举类准入条件（纳税额/开票额/负债率/成立年限/行业）用通用 Handler + 表达式后台可配不发版；全局前置风控等行为类（黑名单/失信/欺诈核验查外部）用专用 Handler（参考 mds RiskBlackRejectHandler 等 30+ 规则 Handler 写法）；运算符 EQ/NE/IN/NOT_IN/IS_BLANK/IS_NOT_BLANK 白名单，未知字段/运算符抛异常不静默通过（对齐 mds RuleConditionEvaluator）

  • 结果五态：PASS / FAIL / SKIP / SKIP_SEGMENT_MISMATCH / ERROR——FAIL 等价 mds 的 REJECT（拒绝）；SKIP_SEGMENT_MISMATCH（客群串访：个人误走企业规则）、ERROR（配置错误告警）为 loan 特有扩展，比 mds 三态（PASS/REJECT/SKIP）更细
  • 双结果审计：step_result + handler_step_result，不一致标 MISMATCH（对齐 mds AdmissionExecutionTrace + AdmissionExecutionRuleLog）
  • 生命周期：0 草稿 / 1 上线 + 写锁；validate-before-enable（字段存在性 / 表达式可解析 / 客群一致性 / 依赖检查）
  • 影子观察：调试中心空跑不落线上（对齐 mds dryRun / globalDryRun）
  • 批量优先：取数/比较/回写一律批量（handleBatch → Map 结果），能批必须批，单号走批量 API list size=1（对齐 mds，支撑 loan 千万级性能）
  • 档位聚合层：引擎执行完毕后按命中产品数与维度通过情况聚合成档位（高/中/低），聚合规则随报告模板版本配置；引擎输出不变，档位是展示层聚合（loan 特有，mds 无）

20线索录入与公海回收体系

小程序与 Web 端均可录入线索；线索分企业/个人双客群，主表 + 双扩展表承载；回收逻辑参考 tse 项目（/Users/admin/Documents/crm/tse）的公海分配与自动回收机制；按千万级数据量设计查询效率。

① 线索分层：主表 + 双客群扩展表

  • 录入的原始线索先落 t_lead 主表（公共字段：lead_type 客群枚举 / 联系人 / phone 加密 + phone_hash / 录入人 / 归属人 / 跟进状态 / ext_json 预留 / source 来源）
  • 客群差异字段进 1:1 扩展表：t_lead_ent_ext（企业名/税号/行业/成立年限/纳税等级/年纳税额/年开票额）、t_lead_person_ext（姓名/年龄/城市/房车/社保公积金/需求额度）——归属/回收/公海/流转/定时任务全部只作用于主表，逻辑只写一份
  • 线索认证通过后才转正为 t_client_profile 客户档案（转正动作记 CONVERT，client_profile_id 双向关联）——线索可被回收/公海流转，客户档案稳定不动
  • 跟进状态机（对齐 tse，双客群同用一套）：NEW 新线索 → INTENTION 有意向 / POTENTIAL 潜在 / VISITED 已拜访 / NO_ANSWER 未接通 / NO_NEED 无意向

② 归属规则：谁录入归谁（限公司员工）

  • 我司老板 / 员工顾问录入：线索归属录入人（owner_uid = recorder_uid），可正常跟进
  • 非公司员工录入（渠道银行用户 / VIP 客户）：线索不归属录入者，直接进公海，由老板指派给顾问跟进；录入侧仅见"我录入了 N 条、转化了 N 条"计数统计，不可见线索明细与进展（与渠道数据边界定稿一致）
  • 录入渠道：Web 管理端（完整表单）+ 小程序线索录入页（移动端快速录入），两端同一套归属规则

③ 回收逻辑（公司员工线索，参考 tse auto_recycle_status_days）

  • 回收控制全部参数化：t_lead_recycle_config 按跟进状态逐行配置——回收开关 / 回收天数 / 预警天数 / 冷却天数四个字段全部后台可改，不写死任何默认值，新增跟进状态行即生效
  • 回收触发：每天定时扫描「超过配置天数无跟进记录（last_followed_at）」的线索 → 自动解除归属 → 进公海
  • 回收前预警：距回收还剩预警天数时，站内消息 + 小程序订阅消息警告归属人「再不跟进将回收」（如剩余 3 天预警，天数可配）
  • 回收后冷却：线索被回收后冷却天数内（默认 7 天可配），原归属人不能认领/被指派（assign_blocked_until，防"占着不跟进、回收了再抢回"）
  • 员工离职转移：老板在管理端「线索公海中心」触发离职转移，该员工名下线索 + 已转正客户一次性全部回公海，由老板重新指派；CRM 员工账号停用事件同步触发提醒
  • 全程留痕：录入/指派/认领/回收/预警/离职转移/转正全部记 t_lead_allocation_record + t_operation_log

④ 公海流转

线索录入→ 归属录入人（员工）/ 直接进公海（渠道·VIP）→ 超期无跟进·自动回收→ 企业公海池→ 老板指派 / 顾问认领→ 跟进·认证·转正客户
  • 公海池内线索对全体顾问可见（基础字段），认领后归属认领人并重新计算回收周期；认领与指派按角色分级（第十八轮定稿）：顾问可认领（冷却期内原归属人不可抢回）、部门主管可本部门内指派与认领、老板全量指派不受限制；工作台「公海认领」快捷操作一键跳转公海池
  • 老板指派不受冷却期限制（冷却仅约束原归属人抢回）

⑤ 双客群流程与 UI 差异

  • 录入表单：客群 Tab（企业 / 个人）切换、字段动态渲染——企业录企业名/税号/行业/年纳税额/年开票额，个人录姓名/城市/需求额度/房车/社保公积金；小程序与 Web 同一套双模板
  • 列表与详情：列表列按客群动态切换（企业列：企业名/税号/行业；个人列：姓名/城市/需求额度），详情页以差异 Tab 展示对应扩展表字段
  • 企业线索（当前主链路）：录入 → 人工跟进 → 引导小程序认证（OCR + 工商核验）→ 匹配·报告 → 转正 t_client_profile
  • 个人线索（占位）：对齐"个人可贷产品暂缓"定稿——录入 → 人工跟进 → 企微人工承接；认证/匹配/转正入口预留但置灰，个人产品上线后直接放开（t_lead_person_ext 已就位，无需改表）

⑥ 千万级数据量 · 查询效率四板斧

  • 联合索引 + 游标分页：列表查询走（owner_uid, 跟进状态, last_followed_at）覆盖索引；深翻页用 cursor（基于 id/last_followed_at），不用 OFFSET；列表查询禁 select *
  • 冷热归档：转正/关闭超 N 天（可配）线索迁 t_lead_archive（结构同主表），主表只留活跃线索；回收定时扫描只查「归属人非空 + last_followed_at 超期」的活跃线索，走索引不扫全表
  • 计数冗余：渠道侧「我录入 N 条 / 转化 N 条」用冗余计数 + 定时校准，禁止对千万级主表 count(*)
  • phone_hash：手机号 AES 加密存储，另存 SHA-256 哈希列承担查重与等值查询（加密不影响索引）；企业线索按统一社会信用代码查重同理留 hash 列
  • 不做物理分区：RANGE 月分区对 MP 分页与全局唯一索引有约束、运维复杂，当前量级靠「归档 + 索引」足够；分库分表属过度设计，明确不做
  • 业务预留：lead_type 枚举可扩展新客群；主表与两张扩展表均带 ext_json，未沟通字段先落 JSON 不改表结构

22图片识别与 AI 信息提取（第二十一轮定稿）

两场景：① 被服务公司（客户）上传资料（营业执照/财报/税单等截图或图片）识别内容；② 合作渠道上架银行产品时用截图/文字提取产品字段。接入 OCR + AI 大模型提取关键信息，自动回填到客户端对应结构化表单。

厂商选型（准确率高 + 价格优化）

  • 标准证照 → 腾讯云专项 OCR：营业执照 BizLicenseOCR / 身份证 IDCardOCR / 增值税发票 VatInvoiceOCR / 表格识别 RecognizeTableAccurateOCR——约 1.1 分/次，精准结构化，与工商核验联动，含复印件/翻拍告警
  • 非标版式（财报/税单/产品截图）→ 通义千问 Qwen-VL 多模态大模型：中文 OCR 识别评分国产第一（准确率高），单价约 $0.52/M（腾讯混元一半价、豆包 1/6 价，价格优）——两者兼得
  • 降本预留：低价模型预筛开关（默认关）——大批量低要求场景可切智谱 GLM-4.5V 先做质量预筛，低质量图直接人工不浪费高价模型调用

识别链路

  • 上传图片 → 类型分流 + 预处理（压缩/纠偏/翻拍检测，图片存阿里云 OSS 复用 tse OssStorageService）
  • 标准证照走腾讯云专项 OCR（精准结构化）；非标版式走 Qwen-VL 多模态提取（自定义字段 KV/表格 + 提示词）
  • AI 结构化提取 → 置信度评分 → 回填表单：高置信度自动带出、低置信度标黄提示；识别仅辅助录入，最终以人工确认为准（防 AI 错别字入仓）
  • 识别记录留痕：t_ocr_record 记录场景/原始图/识别类型/提取 JSON/置信度/人工修正/操作人

两场景落地

  • 客户上传资料：小程序/Web 资料上传时可选「拍照/截图识别」，OCR+AI 提取后回填企业认证/资料提交表单字段（企业名/信用代码/法人/注册资本/税额/开票额等），人工确认后走 t_client_submission 提交 → 匹配
  • 渠道产品上架：渠道端创建产品草稿时支持上传产品截图/文字 → 提取额度/利率/期限/纳税门槛/开票要求等字段回填条件资料结构化表单（biz_terms_json），可编辑后提交走 t_product_approval 产品审核流
  • 合规：AI 提取结果不直接决定匹配结果，仅加速录入；识别原图与提取结果留痕可追溯

落表与技术实现

  • 落表一张：t_ocr_record（识别记录：场景（客户认证/资料提交/渠道产品）/原始文件 key/识别类型（TENCENT_OCR 专项·QWEN_VL 多模态）/提取结果 JSON/置信度/人工修正 JSON/操作人/时间，可追溯 AI 提取轨迹）
  • 策略工厂可插拔：OcrStrategyFactory 多供应商策略（对齐 tse SmsStrategyFactory 模式），新增供应商只加策略实现不改调用方；密钥统一走 Nacos
  • 第三方 Client 封装：参考 tse AliyunOutboundBotClient 封装模式，腾讯云 OCR / 通义 Qwen-VL 各封装独立 Client

23登录用户上下文与注解切面 + 第三方密钥配置项（第二十二轮定稿）

两需求：① 第三方服务密钥做成可配置项；② 登录后构建统一 User 对象，Controller 用 @CurrentUser 注解 + AOP 切面直接拿到当前用户信息。

① 第三方密钥配置项（密钥不硬编码）

  • Nacos 配置中心为主：每个第三方服务一个 @ConfigurationProperties(prefix="loan.xxx") + @RefreshScope 配置类——TencentOcrConfig（loan.tencent.ocr）/ QwenVlConfig（loan.qwen-vl）/ SmsConfig / OssConfig / WechatPayConfig / BizVerifyConfig（工商核验），改密钥改 Nacos 即生效不发版（参考 tse AliyunOutboundBotConfig）
  • 后台可视化：模块 11 系统设置新增「第三方服务配置」页——可视化编辑各服务开关/region/model/endpoint 等参数 + 密钥，落 t_config 配置表（密钥 AES 加密存储），密钥 Secret 后台仅显示脱敏掩码（****），明文只走 Nacos 配置中心，防泄露
  • 动态刷新：@RefreshScope + Nacos 监听，配置变更自动生效，无需重启

② 统一 LoanUser 对象（认证信息里携带）

  • LoanUser 字段：userId（内部ID）+ userNo（客户编号/员工工号/渠道账号）+ phone（手机号）+ name（姓名）+ userType（CUSTOMER 客户·CHANNEL 渠道·STAFF 员工）+ referrer（所属邀请人：inviterNo+inviterName，取自 t_invitation 绑定关系） + region（地区=客户档案城市：个人 city/企业注册地） + avatar（头像）；员工另带 role（BOSS/DEPT_MANAGER/ADVISER）+ deptId，客户另带 invitedFlag
  • 携带方式：JWT 只存轻量（userId+userType）；完整 LoanUser 存 Redis 会话（key=userType:userId，可踢下线）；登录时从客户档案/渠道账号/员工表 + t_invitation 一次性组装 User 对象写 Redis

③ 注解切面注入（核心落地）

  • UserContext：ThreadLocal 持有 LoanUser 对象（参考 tse EnterpriseContext 升级为对象），认证过滤器解析 JWT → Redis 取 User → set UserContext → 请求结束 clear（复用 tse AuthenticationContextSupport 网关头透传/JWT 双通道模式）
  • @CurrentUser 注解 + AOP 切面：Controller 方法参数标 @CurrentUser LoanUser user，切面从 UserContext 取对象注入；@CurrentUser("phone") 可只取某字段；参考 tse AuthenticationGuardAspect / MenuPermissionAspect 切面模式
  • 静态兜底：UserContext.getUser() 供 Service 层非参数场景直接取当前用户；手机号等敏感字段内存明文、出参按需脱敏

落表与技术实现

  • 落表一张：t_config（系统配置项：配置组（TENCENT_OCR/QWEN_VL/SMS/OSS/WECHAT_PAY/BIZ_VERIFY）/配置键/配置值（密钥 AES 加密）/说明/启停，后台可视化编辑 + 密钥脱敏展示）
  • 复用 tse：AuthenticationContextSupport（认证上下文双通道）、EnterpriseContext（ThreadLocal 模式升级为对象）、AuthenticationGuardAspect/MenuPermissionAspect（切面模式）、AliyunOutboundBotConfig（@ConfigurationProperties+@RefreshScope）、EnterpriseCallGateConfig（配置表模式）
  • 全新自研：@CurrentUser 注解、UserContext（ThreadLocal 持有对象）、LoanUser 组装服务（含 referrer 邀请人查询）

24代码开发规范（第二十三轮定稿 · 第二十四轮整合 mds）

后端规范

  • 注释规范：所有类/方法带 Javadoc 注释；接口入参、出参 DTO 每个字段注释说明（含义/是否必填/取值范围）；Controller/Service/Mapper 关键逻辑加行内注释；枚举值注释语义
  • 接口复用：通用能力下沉公共层（facade 门面 / strategy 策略 / util 工具），避免重复代码；同类业务走统一 Service，禁止各写一份
  • 性能与二级缓存：不经常变更的数据用 Caffeine（一级本地）+ Redis（二级分布式）两级缓存——Caffeine 短 TTL 本地热点（字典/规则/菜单/模板/配置），Redis 长 TTL 跨实例共享；统一缓存抽象（CacheService + 注解），避免散落
  • 缓存处理：缓存穿透（空值缓存/布隆过滤器）、缓存击穿（热点互斥锁/热点不过期）、缓存雪崩（TTL 加随机抖动）、缓存一致性（写后失效/延迟双删，数据变更主动 evict 对应 key，参考 tse 教训 B-06 写后 cacheSupport.evict）
  • 代码简洁：单一职责、方法短小、避免大方法与深嵌套；可读性优先于炫技；充分复用 tse 骨架不重复造轮子
  • 不硬编码：配置项/文案/阈值/比例/状态机全部走配置中心或常量类/枚举；魔法值用枚举；第三方参数走 t_config + Nacos
  • 分层包边界（整合 mds）：严格按 controller / service(impl) / repository / dao / entity / execution / rules(handler) / support / enums / config 分层（对齐 mds v2 包），Controller 用 JavaDoc 无 Swagger；跨层不越级调用
  • 渠道差异下沉 Handler（整合 mds）：同类业务多渠道/多客群差异，下沉到独立 Handler/策略子类，禁止在公共 Service 写 if(channelUid==...) 业务分支；公共 Service 只做通用编排（参考 mds market-return-channel-handler SKILL）
  • 批量优先（整合 mds）：取数/比较/回写一律批量（handleBatch → Map 结果），能批必须批，单号走批量 API list size=1；禁止循环内逐条 RPC（支撑千万级性能）

前端规范（对齐 tse-frontend）

  • 按功能分包：views 按模块分包（客户/线索/工单/奖励/短信/组织权限/产品...），组件、工具、API 分层；页面命名与菜单路由一致
  • 公共方法提取 utils：日期格式化、手机号脱敏、金额格式化、状态映射、字典转换等提取到 src/utils；可复用组件提取到 src/components；请求封装、storage、校验统一
  • 前端工具类：request 拦截器（token/traceUuid/错误处理）、formatDateTime/AppDateTime、appConfirm、AppPagination、v-permission 指令等统一工具
  • 注释与后端一致：组件/方法注释、props 入参说明、事件说明；代码简洁、不硬编码
  • 遵循 tse-frontend 教训：el-* 统一、父级仅 redirect 叶子挂 component、keep-alive 用 onActivated、改 script 同步删 template 引用并 npm run build（防白屏）
