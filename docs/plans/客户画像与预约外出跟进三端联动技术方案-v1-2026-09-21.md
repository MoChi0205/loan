# 客户画像与预约、到店、员工外出、跟进回放三端联动技术方案 v1

日期：2026-09-21  
修订：2026-09-21（回写外勤审批口径、接口命名与落地状态）  
状态：**方案基线**。本方案取代 `docs/plans/用户画像与跟踪回放-员工外勤三端联动方案-v1-2026-09-20.md`，两者冲突处一律以本文档为准。P0/P1 已落地，P2/P3/P4 进度见 §8。

## 1. 目标与边界

### 1.1 目标

围绕一个客户档案建立可追踪的服务链路：

`客户画像 → 联系/预约 → 到店或外出服务 → 服务工单 → 跟进记录 → 经营分析与回放`

系统需要支持：

1. 员工查看客户画像、数据来源、分析版本、风险提示和历史变化。
2. 员工记录电话、企微、面谈、预约、到店、外出服务和工单动作。
3. 每日生成来访名单、坐席外出名单、待跟进名单和服务工单清单。
4. 以客户为中心回放完整服务过程，能够回答“谁在什么时间做了什么、基于什么资料、下一步是什么”。
5. Web、H5、小程序共享同一套业务事件和权限规则，但展示内容分层。

### 1.2 不改变的内容

- 银行渠道合作、渠道产品、渠道审批和渠道数据范围不改变。
- 客户端不展示银行产品、准入规则、内部匹配结果、内部评分和员工内部备注。
- 画像结论继续标注数据来源、数据期间、可信度和人工复核状态。
- 不调用免费外部个人信息查询接口；报告固定保留“仅使用客户主动填写及授权上传材料”的说明。

## 2. 当前系统可复用能力

| 能力 | 当前基础 | 本方案处理方式 |
|---|---|---|
| 客户主体 | `t_client_profile`、客户编码、归属顾问、公海字段 | 作为所有事件的主体，不新增第二套客户主档 |
| 客户画像 | 经营分析、报告聚合、材料/OCR、画像字段 | 形成可版本化的画像快照和来源链 |
| 客户跟进 | 客户跟进接口、`last_followed_at`、生命周期事件 | 保留原回收基准，新增独立跟进记录用于完整回放 |
| 服务工单 | `t_service_order`、客户可见/内部备注、状态机 | 作为服务履约主线，预约和到店可关联但不替代工单 |
| 服务沟通 | `t_service_follow` 已有工单沟通表 | 工单内沟通继续使用；客户级沟通另建独立记录，避免强制绑定工单 |
| 权限 | CUSTOMER / CHANNEL / STAFF 与角色范围 | 客户、员工、渠道三种视角分别裁剪 DTO；渠道范围保持不变 |
| 任务调度 | 已有 XXL-Job/定时任务模式 | 用于画像快照、日报名单和 Redis 预热，不在请求链路串行统计 |

## 3. 统一业务对象与数据模型

### 3.1 客户画像快照 `t_client_insight_snapshot`

画像不直接覆盖旧值，而是按版本保存：

| 字段 | 说明 |
|---|---|
| `snapshot_no` | 画像快照业务编号 |
| `client_code` | 客户业务编码 |
| `report_no` | 关联客户报告，可为空 |
| `snapshot_version` | 同一客户递增版本 |
| `dimension_json` | 经营规模、现金流、负债、回款、客户集中度、资料完整度等维度 |
| `risk_flags_json` | 风险提示，不能写成审批结论 |
| `advice_json` | 经营改善建议，仅员工视角 |
| `source_summary_json` | 来源材料、授权时间、数据期间、可信度、核验状态 |
| `generated_at` | 生成时间 |
| `generated_by` | AI / 规则 / 员工复核 |
| `status` | DRAFT / REVIEWED / CURRENT / ARCHIVED |

客户端只读经过裁剪的 `customer_summary`，员工端可读完整画像和来源链；渠道端沿用现有本人客户/报告范围，不新增内部画像字段。

### 3.2 客户级跟进记录 `t_client_follow_record`

用于记录不一定属于工单的电话、企微、面谈和经营咨询：

`client_code`、`staff_code`、`channel_type`、`contact_at`、`content`、`result_code`、`next_action`、`next_follow_at`、`visibility`、`source`、`created_at`。

其中：

- `visibility=CUSTOMER` 只允许展示经过脱敏的服务进度摘要。
- `visibility=STAFF_ONLY` 只进入员工回放，不进入客户 DTO。
- `result_code` 使用字典，如“已联系、待补材料、已预约、已到店、暂缓、无意向”。
- 员工跟进会继续刷新 `t_client_profile.last_followed_at`，不破坏现有自动回收逻辑。

### 3.3 预约与到店 `t_client_appointment`

预约和服务方式放在一个服务事件对象内，减少预约与履约列表不一致。业务上严格区分“公司现场到店”和其他服务方式：

`appointment_no`、`client_code`、`order_no`、`host_staff_code`、`appointment_type`、`scheduled_start`、`scheduled_end`、`location_name`、`location_detail`、`status`、`actual_arrived_at`、`actual_left_at`、`cancel_reason`、`customer_visible_note`、`internal_note`。

已确认的 `appointment_type`：

- `COMPANY_ON_SITE`：公司现场到店，计入“到店人数/到店率”。
- `HOME_VISIT`：员工上门拜访，不计入公司到店统计，计入外出服务统计。
- `VIDEO_MEETING`：视频会议，不计入到店和外出统计。
- `PHONE_CONSULT`：电话咨询，不计入到店和外出统计。

因此“每日来访名单”默认只统计 `COMPANY_ON_SITE`；上门拜访、视频会议、电话咨询分别进入对应服务方式清单。

预约创建与变更规则：

- 支持客户通过小程序/H5主动发起，也支持员工在 Web 端代客创建；记录 `created_by_type`、`created_by_code` 和来源端，方便审计和回放。
- 客户发起后进入 `REQUESTED`，由员工确认；员工代客创建时也必须记录客户、服务方式、时间及客户确认状态，不得省略客户关联。
- 客户和员工均可在预约开始时间至少 5 分钟前自行改期或取消；服务端统一按 `scheduled_start - 5分钟` 校验，不能只依赖前端按钮隐藏。
- 距离预约开始不足 5 分钟或已经开始后，不允许普通改期或取消；确需调整时由员工走异常处理，填写原因并写入操作日志和客户活动时间线。
- 改期不覆盖原记录：原预约标记为 `RESCHEDULED`，创建关联的新预约，以便完整回放。

建议状态：

`REQUESTED → CONFIRMED → ARRIVED → SERVING → COMPLETED`，另有 `CANCELLED / NO_SHOW / RESCHEDULED`。

到店签到优先采用预约二维码或员工确认；GPS 仅在用户和员工明确同意、且确有业务必要时启用，不默认保存连续轨迹。

### 3.4 员工外出 `t_staff_outing`

员工外出不是客户预约的附属字段，应独立记录：

`outing_no`、`staff_code`、`client_code`、`appointment_no`、`order_no`、`outing_type`、`planned_start`、`planned_end`、`submitted_at`、`actual_departed_at`、`departed_location`（密文）、`departed_photo_key`、`actual_returned_at`、`returned_location`（密文）、`returned_photo_key`、`destination`、`purpose`、`status`、`reviewer_staff_code`、`reviewer_name`、`reviewed_at`、`review_remark`、`internal_note`。

状态机包含主管审核环节：

`DRAFT → PENDING_REVIEW → READY → IN_PROGRESS → COMPLETED`，另有 `REJECTED`（可修改后重提）与 `CANCELLED`。

- 外出申请**只能由本人提交**，不接受他人代录：员工工号取登录态，路由参数与请求体都不接受指定员工。
- 提交后进入 `PENDING_REVIEW`，由主管或管理层审核：通过进入 `READY`，驳回进入 `REJECTED` 且必须填写驳回原因，修改后可重新提交。
- **禁止自审**：审核人与申请人必须是不同员工；审核人、审核时间、审核意见全部落库留痕。
- 员工点击“出发打卡”后记录 `actual_departed_at`、`departed_location` 与 `departed_photo_key`，状态进入 `IN_PROGRESS`。
- 员工点击“返回打卡”后记录 `actual_returned_at`、`returned_location` 与 `returned_photo_key`，状态进入 `COMPLETED`。
- 出发和返回均必须打卡，且**必须同时提供现场照片与单点定位**，缺一不得判定打卡成功。
- 每次只在员工主动操作且授权定位后采集一个位置点。
- 不后台持续定位、不保存移动轨迹；定位字段至少包含经纬度、定位精度、位置文本和采集时间。
- 定位或照片上传失败时不得伪造打卡成功，应提示重新授权或按公司异常打卡流程补录，并写入操作日志。
- 打卡照片仅对员工端放开（受角色范围约束），不进入任何客户端 DTO。

### 3.5 统一活动事件 `t_client_activity_event`

这是“跟踪与回放”的读模型，不替代原始业务表：

`event_no`、`client_code`、`staff_code`、`event_type`、`source_type`、`source_no`、`happened_at`、`summary`、`visibility`、`metadata_json`、`created_at`。

事件来源包括：画像生成、材料上传、报告生成、电话跟进、预约创建/确认、到店签到/离店、外出开始/结束、工单创建/状态变化、客户补充资料。

所有事件追加写入，修改采用新版本或更正事件，禁止直接覆盖历史，保证回放可追溯。

## 4. 三端展示方案

### 4.1 Web 员工端：完整经营服务工作台

新增或扩展四个入口：

1. **客户画像与回放**：画像摘要、维度趋势、来源材料、核验状态、风险提示、经营建议、活动时间轴。
2. **今日服务台**：今日来访、待确认预约、正在服务、待回访、今日完成、异常未到店。
3. **外出与坐席**：员工外出登记、出发打卡、返回打卡；按日期、部门、员工、状态查看名单。
4. **服务工单**：保留现有工单列表，增加预约、到店、跟进次数、下一步动作和时间轴入口。

Web 角色范围：

| 角色 | 客户画像/回放 | 今日名单 | 外出 | 工单 |
|---|---|---|---|---|
| 顾问 | 本人客户 | 本人负责/本人坐席 | 本人 | 本人工单 |
| 部门经理 | 本部门客户 | 本部门 | 本部门查看 | 本团队 |
| 老板/运营/超管 | 按现有全量规则 | 全公司 | 全公司配置范围 | 按现有全量规则 |
| 渠道 | 沿用现有本人录入客户/报告范围 | 完全排除 | 完全排除 | 沿用现有渠道边界 |

“名单权限”只约束员工端列表查询的数据范围，包括每日来访名单、预约名单、员工外出名单、待回访名单和服务工单名单：顾问只看本人负责的数据，部门经理看本部门，老板/运营/超管看全公司，渠道账号完全不能访问这些内部名单。名单可见不自动授予修改、取消、打卡或异常处理权限，操作权限需按负责人和角色另行校验。

### 4.2 小程序客户端：服务进度与预约协同

小程序继续以微信一键登录为主，手机号验证码为备用，不新增密码入口。

客户可见：

- 发起预约、选择可用时间段、查看确认/改期/取消结果。
- 查看服务顾问姓名、预约地点，以及“已预约、已到店、服务中、待补充资料、已完成”等服务状态。
- 查看本人可见的跟进摘要和下一步安排；仅展示客户可执行内容，不展示内部备注、内部评分或员工操作信息。
- 到店时扫码签到；查看本人到店记录。
- 上传授权材料，材料继续进入现有 OCR/分析链路。

客户不可见：

- 员工外出明细、员工坐席表、内部跟进全文、内部画像评分、合作渠道和候选产品。
- 其他客户、其他员工的预约和名单。

### 4.3 H5 客户端：分享与预约承接

H5 与小程序共享客户 DTO 和接口权限，重点做三件事：

- 预约链接、改期链接、到店提醒链接可通过短信/企微打开。
- 未登录用户先完成微信/H5 允许的手机号验证码登录，再回到原预约页面。
- 页面只展示客户视角的服务状态和本人记录，不复用 Web 员工详情组件。

如果 H5 还需要给员工使用，应单独确认“员工 H5 模式”；默认不把 Web 内部画像和外出名单下放到 H5。

## 6. 数据分析与性能

### 6.1 分析维度

- 客户生命周期：建档、认证、材料完整度、报告版本、预约、到店、工单、完成/取消。
- 服务效率：首次响应时长、预约确认时长、到店率、爽约率、服务完成率、回访及时率。
- 经营画像变化：资料补齐前后、现金流/回款/负债等维度的版本差异；只使用主动填写和授权材料。
- 员工服务：本人/团队预约量、到店量、待回访、外出时长、工单处理时长。

### 6.2 计算方式

- 请求接口只读快照和聚合表，不串行扫描客户、工单、预约、外出多张大表。
- XXL-Job 每 5 分钟增量生成活动汇总和当天名单；每日凌晨重算前一天并校验差异。
- Redis 缓存：`insight:client:{clientCode}:current`、`daily:appointment:{date}:{scope}`、`daily:outing:{date}:{scope}`。
- 所有写操作发布失效事件；报表缓存按日期和数据范围失效，不使用全库清缓存。
- 建议索引：`(client_code,happened_at)`、`(staff_code,status,scheduled_start)`、`(scheduled_start,status)`、`(actual_arrived_at)`、`(approval_status,planned_start)`。

## 7. 权限、隐私与审计

1. 服务端按 `userType + roleCode + deptCode + owner` 收敛数据；前端隐藏不是安全边界。
2. 客户只能访问自己的预约、到店和客户可见时间线；改写业务编码返回无权或不存在的统一错误。
3. 员工外出地址、签到位置和内部跟进内容按最小必要原则保存；精确位置设置保留期限。
4. 渠道不新增内部画像、员工外出、公司来访名单和跨客户跟踪权限，原渠道合作链路不动。
5. 预约、签到、外出打卡、异常处理、跟进更正、画像复核全部写操作日志；时间线记录操作者、来源端、时间和关联业务对象。
6. 客户端展示的建议仍使用“资料补充/经营改善/咨询准备”等表述，不出现“准入、通过、命中、保证”等承诺性措辞。

## 8. 分阶段落地

### P0：确认业务规则与 DTO（1–2 天）

- ✅ 已确认预约类型、到店定义、外出打卡、客户可见范围和名单数据范围；精确定位保留期限待统一配置。
