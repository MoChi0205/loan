## 一、后端 · 业务编码长度（BizIdGenerator 超长）

| 项 | 内容 |
|---|---|
| **现象** | 点保存报 `Data too long for column 'channel_code' at row 1`（INSERT t_bank_channel 34 字符塞进 varchar(32)）。 |
| **根因** | `BizIdGenerator.generate(prefix)` = 前缀 + 32 位 hex（总长 = 前缀长 + 32）。`generate("ch")` → 34 字符，而 `t_bank_channel.channel_code` / `t_reward_rule.rule_version` 均为 `varchar(32)` → 截断报错。 |
| **修复** | 定长 32 短码改用 `generate(prefix, 32)`：`ProductService.java:259` `generate("ch",32)`、`RewardService.java:364` `generate("rule",32)`。记录级业务 ID（varchar(64)）仍用 `generate(prefix)`。 |
| **防复发** | 写任何定长 32 短码一律 `generate(prefix, 32)`；改完 `grep -rn 'BizIdGenerator.generate("ch")\|generate("rule")' loan-service` 必须零命中。详见 `loan-backend` 实战坑位 + `loan-biz-id`。 |

## 二、权限白名单 · 四处必须对齐

| 项 | 内容 |
|---|---|
| **现象** | 运营（OPERATOR）能进「资源池回收规则 / 认领设置」页面却永远只读，或直接 403；用户反馈「有权限却被判只读」。 |
| **根因** | 角色白名单四处打架：① 前端 `canForceAssign`；② 后端 `ClientController.assign/directAssign` 的 `Arrays.asList(...)`；③ `MiniRoleGuard` 的 `APPROVER_ROLES/APPROVAL_ROLES`；④ 菜单 SQL 授权行。漏写角色（如漏 OPERATOR）即只读/403。历史还有「前端本地硬编码角色判断」与后端不一致。 |
| **修复** | `ClientController.java:118` assign 白名单补 `OPERATOR`（`Arrays.asList("DEPT_MANAGER","OPERATOR","BOSS","SUPER_ADMIN","SUPER")`）；能力标志 `canManage`/`canForceAssign` 改为后端单一真源计算，前端不再本地判角色。 |
| **防复发** | 改角色权限 **四处一起改并 grep 复核**；新增/调整权限前先核对四处方阵。详见 `loan-client-allocation` 红线 2 + `loan-backend` 实战坑位。 |

## 三、企业名称 / 联系人 · 展示补齐

| 项 | 内容 |
|---|---|
| **现象** | 服务总览 / 员工外出 / 客户服务记录 / 订单列表等页面缺失企业名称，用户要求「所有页面都补企业信息字段」。 |
| **根因** | 服务域 DTO（`StaffAppointmentDTO`/`StaffOutingDTO`/`DailyFollowDTO`/`DailyOrderDTO`）与订单出参**未带** `enterpriseName`/`contactName` 字段，前端只能展示业务编码或空。 |
| **修复** | 后端四 DTO 显式加 `enterpriseName`/`contactName` 字段并在组装处 `set`；`OrderService` 列表合并**一次**客户查询补齐（防 N+1）；前端客户列主行 `enterpriseName||contactName` + 副行联系人。工作台缓存 key `v4→v5`（DTO 加字段后弃用旧缓存）。 |
| **防复发** | 新增任何含「客户/企业」的列表，默认补 `enterpriseName`/`contactName` 并由后端合并查询；前端客户列主行企业名 + 副行联系人，**禁止逐行查名称**。详见 `loan-backend` + `loan-web-dev` 实战坑位。 |

## 四、客户认领 / 分配 / 转移 / 资源池 / 回收

| 项 | 内容 |
|---|---|
| **现象** | 用户反复投诉「客户认领和转移逻辑依旧没实现」。 |
| **根因** | 绝大多数「没实现」是**白名单漏角色或前端分流漏分支**，不是真缺代码。后端链路（`ClientAllocationService.applyTransfer`/`directAssign`/`approve`）+ 前端入口（`ClientLookup` 角色分流 / `ApprovalCenter` allocation tab）本已齐全。 |
| **分级流转（唯一真源）** | ① 无归属 → 直接认领（CAS 防并发重复）；② 本人 → 幂等；③ 经理/老板/超管 → `directAssign`（经理仅本团队，BOSS/SUPER 跨团队）；④ 顾问跨团队 → `applyTransfer` → `ADVISER_TRANSFER`，跨团队两级 `TEAM_REVIEW→BOSS_REVIEW`。 |
| **资源池创建权限** | 仅 经理/老板/超管 可创建；渠道只读本人录入、无公海无认领。 |
| **配额三维度** | `LEAD` / `CLIENT` / `POOL:<poolCode>`；认领时资源池优先 → 回落公海类型；前端必须支持新增/删除/筛选行（禁固定两行静态渲染）。 |
| **回收 0 语义** | 显式配 0 = 当天回收；留空 = 不回收。后端 `parseStatusDays` 保留 0 项（`days!=null` 即存），`recycleDays` 仅 `null` 视为未配置；删 `days>0` 过滤与 `DEAL/SIGNED/NO_NEED` 硬编码 `return 0`。 |
| **防复发** | 改归属/配额/回收前先查后端链路与白名单四处对齐，再改。详见 `loan-client-allocation` 技能（含自检清单）。 |

## 五、日期组件宽度统一（AppDateTime width prop）

| 项 | 内容 |
|---|---|
| **现象** | 服务总览 / 员工外出 / 客户服务记录等页面日期框铺满整行、与下拉框/表格列宽失衡；用户反复要求「适配页面布局而非一味填满」。 |
| **根因** | ① 管理端并存 3 个日期组件（AppDateTime 缺省回落 100% / AppDateRange 固定 260 / ServiceDateTimeRange 硬编码 100%+min 320）能力重叠、规格各写各的；② 页面 `:deep` 覆盖日期宽度与组件 `width` prop 打架（Element Plus picker 根 div 透传 `$attrs.style`，内联优先级最高）。 |
| **修复** | 以 `AppDateTime` 为唯一组件，缺省宽度按 type 定死（date 200 / datetime 220 / daterange 260 / datetimerange 360），根元素 `flex:0 0 auto`；筛选条显式传 `width`，表单内才传 `width="100%"`；删除页面 `:deep` 覆盖日期宽度的 CSS 规则（单一真源 = 组件 prop）。 |
| **防复发** | 筛选条用 `AppDateTime` 并传 `width`；**不要在页面 style 里 `:deep` 覆盖日期宽度**。详见 `loan-web-dev` 实战坑位。 |

## 六、前端筛选"假筛选"

| 项 | 内容 |
|---|---|
| **现象** | 加了对接下拉/日期控件，但筛不动（如附件下载审核、客户分配审核、短信/报告模板审核、渠道档案缺筛选）。 |
| **根因** | `useTable` 会把 query 整体透传，但**后端不接收的参数就是假筛选**（前端加了"筛了无效"）。加筛选前三处没对齐。 |
| **修复** | 补筛选 = 前端控件 + 后端 `@RequestParam` 接收 + `LambdaQueryWrapper` 条件 **三件套一起做**，禁只改前端。涉及 `ApprovalController/ApprovalService`（download/allocation 日期）、`unifiedPending`（日期+提交人）、`/report/template/page`（日期+创建人）等。 |
| **防复发** | 加任何筛选前先核对后端 Controller 是否接收该参数；后端没加就联动后端。详见 `loan-backend` + `loan-web-dev` 实战坑位。 |

## 七、统计/列表口径一致（计数 vs 列表）

| 项 | 内容 |
|---|---|
| **现象** | 「新用户(1)」chip 点击后列表 0 条；角标计数与列表不符。 |
| **根因** | 计数 SQL（`ClientProfileMapper.tagCountKey`）把 `customer_tag` 为 NULL/空/未知值全计入 newCount，列表过滤 `ClientService` 用 `customer_tag = 'NEW'` 精确匹配（NULL 不命中）→ 计数 1、列表 0。 |
| **修复** | 列表 NEW 分支改为 `customer_tag IN ('NEW') OR IS NULL OR = ''`（与计数侧对齐），保留排除已成交/已预约的 `notExists`。 |
| **防复发** | 改计数口径必须同步对齐列表 where；chip 计数与点击后列表过滤条件必须同口径。详见 `loan-backend` / `loan-web-dev` 实战坑位。 |

## 八、哨兵值展示（remaining = -1）

| 项 | 内容 |
|---|---|
| **现象** | 手机号首次查看提示「本日剩余 -1 次」。 |
| **根因** | `-1` 是后端「豁免角色不限次」哨兵值（`SensitiveViewService.getQuota` 对 BOSS/超管/运营返回 remaining=-1），前端原样显示。 |
| **修复** | 显示 remaining 处统一：`remaining < 0` → 显示「不限次数」，不裸显 -1。 |
| **防复发** | 后端哨兵值（如 remaining=-1 表示不限）前端展示前必须判断语义，别直接打在 UI 上。详见 `loan-backend` / `loan-web-dev` 实战坑位。 |

## 九、前端初始化时序（刷新弹回工作台）

| 项 | 内容 |
|---|---|
| **现象** | 点开/刷新「资源池回收规则」等非工作台页面总是被弹回工作台（疑异常被吞）。 |
| **根因** | `Layout.initializeLayout` 先 `await loadRoleMenu()` 后 `loadTabs()`；loadRoleMenu 内「当前 fullPath 不在 openTabs 则 replace 回退」，但此刻 tabs 尚未从 localStorage 恢复（空+工作台）→ **刷新任何非工作台页都被弹回**。 |
| **修复** | 顺序改为 `loadTabs()` → `await loadRoleMenu()` → `ensureTab()`：先恢复持久化标签，权限兜底判断才有正确输入。 |
| **防复发** | 初始化时序：先恢复持久化标签/状态，再查权限/菜单。属前端坑位，影响认领/分配页可用性。详见 `loan-web-dev` 实战坑位。 |

## 十一、错误分支按 code 不按文案

| 项 | 内容 |
|---|---|
| **现象** | 跨团队转移等业务异常，前端按 `e.message.includes('跨团队')` 判断，文案一变就落到静默兜底（用户只见"系统错误"）。 |
| **根因** | 匹配中文文案在异常包装 / 文案微调后即失效。 |
| **修复** | 后端新增专属语义码（如 `CLIENT_CROSS_TEAM=1005`）到 `ResultCode`，`BusinessException(ResultCode.XXX, msg)` 抛出；前端按 `e.code` 分支。 |
| **防复发** | 错误分支按后端 `code` 判断，禁匹配中文文案；全局兜底不得吞掉业务 message。详见 `loan-backend` / `loan-web-dev` 实战坑位。 |

| **防复发** | 动手前**必** `git status --short` + `git diff <file>` 看清未提交改动；发现别人的在途改动不覆盖、不重复实现，改为验证并汇报。详见 `docs/local-brain/06-fix.md` 与项目工作约定。 |
