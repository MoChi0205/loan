> **最新更新（2026-08-30）**：与知识库 `04-后端 API 契约.md` 逐接口校正一致（修正 `match/report/*`→`report/*`、`{no}`→`{code}/{approvalNo}/{reportNo}/{orderNo}`、`login-bind` 废弃并合并进 `login.inviteCode`）；同步新增知识图谱 `09-业务流程知识图谱.md` + 机器可读 `09-...json`；配套可视化 `artifacts/企融通业务流程图.html`。本文件为接口真源，KB 09 为其结构化派生，流程图为其可视化派生。

> 文档定位：本文在《方案评审定稿纪要》《小程序整体功能方案》《loan-mini-实施规格 V3.0》《交互方案》与知识库结论（C1–C19）基础上，**逐模块**给出「用户交互流程 → 触发动作 → 后端接口 → 请求/响应契约 → 角色分支 → 状态机/边界」的完整设计，作为前端（loan-mini）/ 后端（loan-service）联调与评审的唯一接口真源。
>
> 数据来源：已读 `loan-service` 全部 `com.loan.mini.controller.*` 与 `sms` 控制器源码，接口路径、参数、权限、响应字段均来自真实代码（非旧文档推测）。旧文档中不一致处已按代码校正并标注。
>
> 通用约定：
> - Base URL：`/loan/api/mini/*`（小程序）；管理端 `/loan/api/admin/**`（统一鉴权拦截器）。
> - 鉴权头：`Authorization: Bearer <token>`，由 `@CurrentUser LoanUser` 注入；匿名访问仅登录/短信/企微活码。
> - 返回包：`Result<T>{ code, message, data }`，`code=0` 成功；分页 `PageResult<T>{ page, size, total, records }`。
> - 字段命名红线：`contactName`(客户姓名) / `entName`(企业名) / `clientCode`(客户编码) / `reportNo`(报告号) / `approvalNo`(审批单号) / `ownerStaffCode`(归属人工号) / `ownerStaffName`(归属人姓名) / `totalResult∈PASS|CONDITION|REJECT|SKIP_SEGMENT_MISMATCH|ERROR`。
> - 敏感脱敏：手机号返回 `138****0001`；产品名/银行名对客隐藏（仅企业员工可见，见 C4）。

## 1. 登录 / 鉴权 / 企业认证

### 1.1 角色权限
全部角色通用。客户走企业/个人认证；渠道/员工登录后直接进对应工作台。

### 1.2 交互流程
1. 首次进入 → 调 `GET /me`；无 token → 进登录页。
2. 登录页 → `POST /auth/login`（微信 `code` 主通道）→ 拿到 `token` + `LoginResponse` → 存 `loan_token`。
3. 登录成功 → 再次 `GET /me` 拉 `roleInfo` 与档案 → 写入 `store.user` → `uni.reLaunch` 到角色首页。
4. 客户若未认证 → 首页弹「企业认证」引导 → `POST /auth/enterprise`。
5. 带邀请码进入 → 登录时可一并传 `inviteCode`（已合并进 login，旧文档 `login-bind` 已废弃）。

### 1.3 接口清单

| 编号 | 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|------|
| A1 | POST | `/api/mini/auth/login` | 公开 | 微信登录；兼容开关开时可用 `{phone, code}` 短信验证码登录（管理端建档） |
| A2 | GET | `/api/mini/me` | 已登录 | 档案摘要 + `roleInfo{userType, roleCode, role}` |
| A3 | POST | `/api/mini/auth/enterprise` | CUSTOMER | 企业认证 `{creditCode, enterpriseName, contactName?}` |
| A4 | GET | `/api/mini/wecom/qrcode` | 公开 | 企微客服活码 URL |
| A5 | POST | `/api/sms/send-code` | 公开 | 发送验证码 `{phone}` |
| A6 | POST | `/api/sms/verify-code` | 公开 | 校验验证码 `{phone, code}` |

### 1.4 关键响应
```
A1 返回 LoginResponse = { token, userNo, userType, roleCode, name, phone(masked), role }
A2 返回 { ...profile字段, roleInfo:{ userType, roleCode, role } }
```
**分支说明**：`role` 由后端 `resolveRoleInfo()` 推导，与前端 `resolveRole()` 同步；映射中心在后端，前端不可自行改判（防越权）。

## 4. 智能匹配（match）— 核心模块（C1/C2/C10/C19）

### 4.1 角色权限
- ✅ 客户：仅对自己已认证企业发起。
- ✅ 企业员工（除渠道）：可替客户匹配（C2 替客匹配）。
- ❌ 渠道：禁入（后端 `MiniMatchController.run` 显式拒绝，前端 match 守卫 `!isStaff && !store.isAuthed` 拦截）。

### 4.2 交互流程（4 步 + 0 步查重）

```
[步骤0 选择/锁定目标企业]
  ├─ 客户：默认本人已认证企业，跳过查重
  └─ 员工(C2/C10)：输入「企业名/手机号」→ 实时查重
        ├─ 命中 → 显示 dup-card + 「申请分配」按钮 (→ 4.3 归属流转)
        └─ 未命中 → 录入新客户表单 → 「创建并归属」 (→ 4.3 情形A)

[步骤1 填写经营事实]   企业经营事实（纳税/开票/成立年限/行业…）

[步骤2 上传经营材料]   经营数据/年报/附件/照片（OSS 直传，引用 clientSubmitId 幂等键）

[步骤3 确认匹配条件]   申请城市/产品偏好等

[步骤4 发起匹配+生成报告]  底部主操作仅在 step-card 内（第4步隐藏底部按钮，C13）
        → POST /api/mini/match/run
        → 返回 MiniMatchResult（仅数量+评级，对客脱敏）
        → 跳「我的报告」查看报告详情
```

> 注意（C13/C10）：查重自动判定替代手动 seg；录客户「申请分配」按钮用 `btn-primary`；上传补充材料按钮不铺满。

### 4.3 客户归属流转状态机（C2 + C19）

```
              员工发起替客匹配
                    │
        ┌───────────┴───────────┐
   系统中无该企业(情形A)     系统中已有该企业(情形B)
        │                          │
   录入基础数据                有归属人？
   自动归属当前用户              ├─ 是 → AUTO_CLAIMED（自动归属，无审批）
   (POST /client)               └─ 否(公海/无主) → PENDING_APPROVAL
   action=CREATED                  │
                                    ├─ APPROVED → 归属流转给当前用户
                                    └─ REJECTED → 驳回(opinion必填)
```

### 4.4 接口清单

| 编号 | 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|------|
| M1 | POST | `/api/mini/match/run` | CUSTOMER/STAFF（CHANNEL禁） | 发起匹配，body 可带 `clientCode`（替客必传） |
| M2 | GET | `/api/mini/match/history` | CUSTOMER | 我的匹配历史分页 |
| M3 | GET | `/api/mini/client/search?keyword=` | STAFF（CHANNEL禁） | 查重（≥2字，任一字段命中） |
| M4 | POST | `/api/mini/client` | STAFF | 录入新客户并自动归属 |
| M5 | POST | `/api/mini/client/{code}/claim` | STAFF | 申请分配（自动/待审） |
| M6 | GET | `/api/mini/client/{code}/claim-status` | STAFF | 审批状态轮询 |
| M7 | GET | `/api/mini/client/allocation-approvals/pending` | OPERATOR/SUPER/BOSS | 待审列表 |
| M8 | POST | `/api/mini/client/allocation-approvals/{no}/approve` | OPERATOR/SUPER/BOSS | 通过→归属流转 |
| M9 | POST | `/api/mini/client/allocation-approvals/{no}/reject` | OPERATOR/SUPER/BOSS | 驳回 `{opinion}` 必填 |

### 4.5 关键请求/响应
```
M1 请求体：{ facts:{...}, applyCity?, clientSubmitId?, clientCode? }
   权限分支：
     - 客户：clientCode 强制用登录态，忽略 body.clientCode（防越权替客）
     - 员工：body.clientCode 必传（步骤0已锁定归属），缺失报 PARAM_ERROR
M1 响应 MiniMatchResult：
   { reportNo, grade(HIGH/MIDDLE/LOW), totalResult(PASS|CONDITION|REJECT),
     productCount, rating, ruleLogs:[{...脱敏规则说明}] }
   ⚠ 对客仅返回数量+评级，禁止产品名/银行名/额度/利率（合规红线）

M3 响应：命中客户对象 { ..., hasOwner } 或 null
M4 响应：{ clientCode, ownerStaffCode, action: CREATED|EXISTED }
M5 响应：{ result: AUTO_CLAIMED|PENDING_APPROVAL, approvalNo? }
M6 响应：{ status: PENDING|APPROVED|REJECTED, rejectReason? }
```

## 9. 渠道产品管理（product）— C9 状态机

### 9.1 角色权限
- 录入/管理：仅 CHANNEL（自有产品，沙箱隔离）。
- 删除终审：仅 STAFF（运营/超管；C19 后也含 BOSS 审批中心）。

### 9.2 产品状态机（C9）
```
 DRAFT ──submit──▶ PENDING ──(运营终审通过)──▶ OK(已上架)
   ▲                  │                          │
   └────revoke────────┘                 delete-apply
                                        │
                                   PENDING_DELETE ──audit(approve)──▶ 物理删除(软删+t_audit_log)
                                        │                          └──audit(reject)──▶ OK
                                        └────delete-cancel──────────▶ OK
```
- 撤销审批：PENDING → DRAFT（即时，无需审批）。
- 删除申请：OK → PENDING_DELETE（需运营/超管终审）。
- 撤回删除：PENDING_DELETE → OK。

### 9.3 接口清单

| 编号 | 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|------|
| P1 | GET | `/api/mini/product/list` | CHANNEL | 我的产品（沙箱自有） |
| P2 | POST | `/api/mini/product` | CHANNEL | 保存（新建草稿/编辑重提），`bankProductCode` 必填 |
| P3 | GET | `/api/mini/product/{code}` | CHANNEL | 详情（编辑回填） |
| P4 | PUT | `/api/mini/product/{code}` | CHANNEL | 编辑（按 code 定位审批单） |
| P5 | POST | `/api/mini/product/{code}/submit` | CHANNEL | 提交审批 |
| P6 | POST | `/api/mini/product/{code}/revoke` | CHANNEL | 撤销审批 |
| P7 | POST | `/api/mini/product/{code}/delete-apply` | CHANNEL | 申请删除 `{reason}` |
| P8 | POST | `/api/mini/product/{code}/delete-cancel` | CHANNEL | 撤销删除 |
| P9 | GET | `/api/mini/partner-product/delete/pending` | STAFF | 待删除列表 |
| P10 | POST | `/api/mini/partner-product/delete/{no}/audit` | STAFF | 终审 `{approve:bool, opinion}` |

### 9.4 关键响应
```
P2 响应：{ code, action: CREATED|UPDATED }
P9 响应：待删除产品列表（含 reject 后回 OK 的原因展示）
```

## 12. 错误码与边界

| code | 含义 | 前端处理 |
|------|------|----------|
| UNAUTHORIZED | 请先登录 | 跳登录页 |
| FORBIDDEN | 无权操作（渠道禁匹配/客户查产品/越权） | 提示并收口入口 |
| PARAM_ERROR | 参数错误（如员工匹配缺 clientCode） | 表单校验提示 |
| DATA_NOT_FOUND | 数据不存在 | 空态 |
| COMMON_ERROR | 系统繁忙 | 重试/error 态 |

**全局强制规则（后端兜底，前端不可信赖本地判断）**：
- 客户报告/工单查询：后端强制仅自己，前端传的跨用户参数一律忽略。
- 渠道：匹配/报告/产品明细/工单均显式 `FORBIDDEN` 或返回空。
- 员工替客匹配：`clientCode` 必传且以归属校验为前提。

## 14. 业务流程全景与知识图谱索引

> 本节为「分模块细节（§1–§13）」的上方综合视图，配合 `docs/knowledge-base/09-业务流程知识图谱.md`（结构化节点+边）与 `artifacts/企融通业务流程图.html`（可视化）使用。三者口径一致、以源码为唯一真源。

### 14.1 端到端业务流程（泳道概览）

| 阶段 | 客户 CUSTOMER | 企业员工 STAFF（除渠道） | 渠道 CHANNEL | 运营/老板/超管 |
|------|---------------|--------------------------|--------------|----------------|
| 进入 | 登录→企业认证→首页 | 登录→首页（5 tab） | 登录→首页（3 tab：我的产品/我的） | 登录→首页（5 tab） |
| 核心 | 智能匹配（仅自己企业）→ 报告（仅自己/日期） | 替客匹配（查重→归属流转）→ 报告（全量四维）→ 命中产品/诊断 | 我的产品（录入→审批→上架/删除终审） | 审批分配单 + 终审产品删除 |
| 衍生 | 服务单（自己）/ 邀请奖励 / 线索录入 | 服务单（全量）/ 客户管理（规划） | — | 线索公海（规划） |

### 14.2 模块依赖与触发顺序

1. `M_AUTH` 登录/认证 → `M_NAV` 角色化导航（reLaunch）→ `M_HOME` 首页分流
2. 客户/员工：`M_HOME` → `M_MATCH` 智能匹配（员工先走 `M_ALLOC` 查重→归属流转）→ `M_REPORT` 报告 → `M_PRODUCTS`(员工)/`M_DIAG`/`M_ORDER`
3. 渠道：`M_HOME` → `M_CHANPROD` 产品管理（删除终审回 `M_ALLOC` 审批）
4. 支线：`M_INVITE` 邀请奖励、`M_LEAD` 线索录入（不阻塞主线）
