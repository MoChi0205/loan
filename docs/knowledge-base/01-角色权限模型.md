# 01 · 角色权限模型

## 7 角色体系（必须严格区分）

| 角色 | userType | roleCode | 主要场景 |
|------|----------|----------|---------|
| 客户 | CUSTOMER | （无） | 自助使用小程序 |
| 渠道合作方 | CHANNEL | （无） | 录入产品/线索；只读本人录入形成的客户、报告与归属姓名（D50） |
| 顾问 | STAFF | ADVISER | 替客户匹配 / 全量陪访 |
| 部门经理 | STAFF | DEPT_MANAGER | 同顾问 + 团队归属 |
| 老板 | STAFF | BOSS | 同顾问 + 全量 |
| 运营管理员 | STAFF | OPERATOR | 配置/审批/审计；**小程序侧承载轻，主体在 Web** |
| 超级管理员 | STAFF | SUPER_ADMIN / SUPER | 同运营；两个角色码双写兼容 |

> **关键**：C1 已确认「客户（自身）+ 全部企业员工（STAFF，渠道除外）均可操作智能匹配」；**渠道合作方是唯一不可操作匹配的角色**。

### Web 权限链路真值（D53）

- 页面准入以后端动态菜单 path 为真值，前端静态路由仅是组件映射；子路由必须显式继承父菜单。
- 完整验收链路为：角色菜单 → 前端路由 → 页面实际首屏 API → 网关 → Controller 角色守卫 → 数据范围。
- 业务默认全量角色为 `BOSS/OPERATOR/SUPER_ADMIN/SUPER`；应用内与网关使用同一角色集，新增业务接口不依赖逐条回填 `t_role_api`。
- `BOSS` 仅业务全量，不是系统配置管理员；其对组织写、角色/菜单/接口权限、调试中心的显式拒绝优先于默认全量。
- 系统配置管理角色为 `OPERATOR/SUPER_ADMIN/SUPER`；渠道内容终审只有 `BOSS/SUPER_ADMIN/SUPER`，不含 `DEPT_MANAGER/OPERATOR`。

### 渠道 Web 沙箱（D50）

- 菜单：工作台、我的线索、我的客户、我的产品、客户分析报告。
- 渠道有权新增线索；新增成功后立即进入本人“我的线索”，待审批、已通过、已驳回均可查看，不因审批状态隐藏。
- 仅本人录入线索所形成的客户可见；报告必须属于这些客户；归属只显示顾问姓名。
- 公司公海仅接收审批通过并转为 `NEW` 的渠道线索，`PENDING_APPROVAL/REJECTED` 不进入公司公海。
- 不可编辑档案、发起匹配、查看命中产品明细、认领、指派、转移或回收客户。
- 数据隔离以服务端 `userNo → t_lead → clientCode → reportNo` 为准，不能依赖菜单隐藏。

## 分享引荐与服务顾问归属

- 分享小程序链接或二维码时自动携带邀请码；新客户在有效期内登录后自动绑定引荐链，无需手工填写。
- 引荐关系只记录 `referrerName/referrerClientCode`，不写入 `ownerStaffCode`，分享人不等于服务顾问。
- 新微信客户若 `ownerStaffCode` 为空，即进入 Web「未分配客户」池。顾问可申请认领，管理角色可按客户业务编码选择顾问并发起分配；两类入口都创建 `ALLOCATION` 待审单。
- `DEPT_MANAGER` 可发起管理分配并**直接落归属（无需审批）**（`POST /api/admin/client/{clientCode}/assign`，目标=ADVISER/DEPT_MANAGER，覆盖式重分配）；同时 `DEPT_MANAGER` 已纳入 `ALLOCATION` 审批人，**仅可审批本人团队**（申请人部门==本人部门）的待审单，跨团队须由 `BOSS` 审批（D39 / C24）。`BOSS/OPERATOR/SUPER_ADMIN/SUPER` 可审批全部。
- 小程序「我的」展示真实服务顾问姓名和引荐人姓名，不把员工工号、客户编码等内部编码作为可见信息。

## 后端：LoanUser 字段

```java
com.loan.context.LoanUser {
  Long userId;
  String userNo;          // 员工工号（员工）或 clientCode（客户）
  String phone;
  String name;
  String userType;        // CUSTOMER / CHANNEL / STAFF
  String referrerNo;
  String referrerName;
  String region;
  String avatar;
  String roleCode;        // 仅 STAFF 有：ADVISER/DEPT_MANAGER/BOSS/OPERATOR/SUPER_ADMIN/SUPER
  String deptCode;
}
```

- 通过 `@ControllerUser` 注解 + 拦截器注入。
- 前端通过 `/api/mini/me` 拿到 user（注意：小程序端 user 包含 userType + roleCode）。

## 前端：Pinia store（store/user.js）

```js
state: {
  token, clientCode, user, profile,
  invitedFlag, authStatus,           // UNAUTHED / ENTERPRISE / PERSONAL
  referrerName,
  role: 'customer' | 'channel' | 'adviser' | 'deptmgr' | 'boss' | 'operator' | 'super'
}

getters: {
  isLoggedIn,                        // !!token
  isAuthed,                          // authStatus !== 'UNAUTHED'
  isChannel,                         // role === 'channel'
  isStaff,                           // ['adviser','deptmgr','boss','operator','super'].includes(role)
  roleLabel                          // 用于「我的」页与徽章
}
```

### 角色推导（resolveRole）

`userType=CUSTOMER` → customer
`userType=CHANNEL` → channel
`userType=STAFF` + roleCode → adviser / deptmgr / boss / operator / super
`roleCode` 未识别 → adviser（最小可用权限兜底）

### 角色持久化

- storage key：`loan_role`（同 token 的 loan_token）
- `/api/mini/me` 返回 `roleInfo`（含 userType + roleCode + role）
- `setUser` / `init` / `refreshProfile` 触发角色写入与持久化

## 角色化导航（C17）

- 自绘 `components/TabBar.vue`，`store.role` 驱动 tabList
- **客户/员工**：5 tab（首页·智能匹配·我的报告·服务单·我的）
- **渠道小程序**：仍为 4 tab（首页·我的产品·录入客户·我的），隐藏匹配/报告/服务单；D50 只新增 Web 只读入口
- 切换一律 `uni.reLaunch`（**禁用 `uni.switchTab`**，无 tabBar 配置会失败）

## 常见错误

| 现象 | 原因 | 排查 |
|------|------|------|
| 客户视角看到全部功能 | `store.role` 默认为 customer 但 getter 误判 | 检查 `isStaff` getter，role 必须是字符串数组包含项 |
| 渠道被允许匹配 | `isChannel` 未在 match 守卫 | 在 `MiniMatchService.run` 前加 `requireChannelGuard()` |
| 切换用户后菜单不变 | 切换没触发 reactive 重渲 | `pickRole` 后需 `store.setUser(data.user)` 触发 role 更新；reLaunch 后新页面读 store 渲染 |
| 渠道显示员工 tab | TabBar.vue 的 `store.isChannel` getter 没拿到最新值 | Pinia getter 引用 `state.role`，state 写入必须 `this.role = ...`（不能 `this.$state.role`） |
