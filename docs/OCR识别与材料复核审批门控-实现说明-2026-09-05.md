# OCR 识别管线升级：VLM 视觉抽取 + 材料复核审批门控

> 日期：2026-09-05
> 模块：loan-service（Spring Boot + MyBatis-Plus） / loan-mini（uni-app 小程序）
> 目标：打通「上传文件 → 大模型识别 → 我司审批通过后才回灌客户数据」的端到端管线

---

## 一、现状澄清（你之前的问题）

你问「当前代码用上传文件由后端识别信息、再做分析报告，但不知系统采用何种方式处理客户数据」。读完本地代码后结论是：

- **原来的识别器 `MockOcrExtractor` 永远返回空 Map**——整条管线「已接线、未通电」：上传→落盘→`t_ocr_record` 留痕都正常，但**没有任何真实识别引擎在跑**，所以也就无所谓「如何处理客户数据」。
- `OcrService` → `SubmissionFactsMerger`（仅补空不覆盖回灌）→ `ScreeningService` 这条链路本身是完整的，只是前面没有数据产出。
- `OcrService.recognize` 中 `ocr_type` 写死为 `TENCENT_OCR`，即使接了引擎也不会正确留痕。

本次升级就是把这条管线真正「通电」并加上**审批门控**：识别结果在我司审批通过前，**绝不进入客户可见数据**。

---

## 二、方案（经你确认的两个决策）

1. **识别引擎 = 大模型视觉抽取（VLM）**：OpenAI 兼容的 chat/completions 多模态接口（通义千问 VL / GLM-4V / 本地 vLLM 均可）。
2. **联动形态 = 审批门控**：上传 → 大模型分析 → 提交「材料复核」待审 → **我司审批通过后**才回灌提交单并置客可见。

---

## 三、架构与数据流

```
小程序上传(MiniUploadController)
   │  fileKey, bizType, clientCode, reportNo
   ▼
MiniMaterialService.ingest
   │  OcrService.recognize  → ① OcrExtractor.extract(可插拔)
   │                              ├ mock (默认, 返回空 Map, 不激活)
   │                              └ vlm  (VLM, 真实抽取 → 原始字段)
   │                         ② OcrService.mapToFacts 按 t_extract_field_def 映射为规范 facts
   │                         ③ t_ocr_record 留痕 (ocr_type=mock/vlm)
   ▼ facts 非空 ?
   ├─ 否 (mock/未配置): 向后兼容，不触碰客户数据
   └─ 是: MaterialReviewService.createPending
            → 写 t_material_review(PENDING_REVIEW)
            → t_ocr_record.review_status=PENDING_REVIEW, visible_flag=0
            →【事实仅存 pending_facts_json，绝不回灌客户提交单】
                       │
                       ▼ (审批中心)
MiniApprovalController /approval/pending?type=MATERIAL_REVIEW
   → ApprovalService.unifiedPending → materialReviewPage (列表携带 pendingFactsJson 供审批人查看)
                       │
                       ▼ 审批动作 /approval/MATERIAL_REVIEW/{reviewNo}/audit
ApprovalService.unifiedAudit → MaterialReviewService.audit
   ├─ 通过: backfillSubmission
   │          ├ 有 reportNo → SubmissionFactsMerger.mergeFromOcr (仅补空不覆盖, 复用既有铁律)
   │          └ 无 reportNo → SubmissionService.submit 按 facts 新建提交单
   │        + t_ocr_record.visible_flag=1, review_status=APPROVED (客可见)
   └─ 驳回: review_status=REJECTED, 识别结果作废、永不回灌
```

**关键红线（与既有规则一致）**：审批通过后的回灌复用 `SubmissionFactsMerger.mergeFromOcr` 的「仅补空不覆盖」语义，与用户手填值互不冲突；审批前识别结果一律隔离在 `t_material_review`。

## 五、部署 / 激活步骤

1. **执行 DB 迁移**：`db/migrate-material-review-gating-2026-09-05.sql`（`t_ocr_record` 加列、建 `t_material_review`、写入字段映射种子）。
2. **配置 VLM（激活真实识别）**：在 `application.properties` 中
   ```
   loan.ocr.provider=vlm
   loan.ocr.vlm.base-url=https://你的兼容网关/v1
   loan.ocr.vlm.api-key=sk-xxx
   loan.ocr.vlm.model=qwen-vl-max        # 可选覆盖
   loan.ocr.vlm.timeout-ms=60000
   ```
   - 不配置 base-url / api-key 时，VLM 抽取器**降级返回空 Map**，应用照常启动、上传照常（不识别、不门控），与 mock 行为一致。
3. **审批白名单**：`loan.mini.approval.types=ALLOCATION,MATERIAL_REVIEW` 已含 `MATERIAL_REVIEW`，审批中心自动纳入，无需改 Controller 路由。
4. **字段映射种子**：`t_extract_field_def` 已写入 9 条（企业名称/信用代码/行业/成立年限/年纳税额/年开票额/年营收/从业人数/注册资本），模型返回的原始字段别名经 `sourceKeys` 命中后映射为规范 facts；如需补充字段，加种子即可，无需改代码。

## 六、验证要点 & 已知限制

- **环境无 Maven**（`mvn` 不可用、无 wrapper），本次改动未做编译校验。请在本机用 IDE/Maven 编译 `loan-service` 确认；重点核对：`MaterialReviewService` 的 import 与注入、`PageResult.build` 调用签名、`resolveSubmissionNoByReport` 中 `ClientScreening`/`ClientSubmission` 的字段访问器。
- **上传触发条件**：`MiniUploadController` 仅在 `reportNo` 非空时才调用 `ingest`（沿用原 T2 设计）。若要让「无报告号、仅客户档案的材料上传」也走识别+门控，需放宽该 `if` 条件（当前保留原语义，避免意外扩大识别面）。
- **审批详情接口**：小程序审批中心复用了待审列表内联的 `pendingFactsJson` 展示识别结果，未单开 detail 接口；如需独立详情页，可暴露 `ApprovalService.materialReviewDetail` 并加 Controller 路由。
- **`materialReviewPage` 计数**：`total` 固定取 `PENDING_REVIEW` 计数；若按 `status=APPROVED/REJECTED` 查询历史，列表会按状态过滤但 total 仍为待审数（待审列表场景下无影响，历史查询如需精确计数再补）。
- **`MiniMaterialService.ingest` 的兼容分支**：facts 为空时不会进入即时回灌（本就无事实可回灌），与「审批前不触碰客户数据」一致。

---

## 七、一句话总结

原管线是「mock 未激活、已接线未通电」；现已升级为 **VLM 可插拔识别（默认 mock 不破坏启动）+ 材料复核审批门控（审批前识别结果隔离在 `t_material_review`，通过后复用既有的「仅补空不覆盖」回灌并置客可见）**，端到端贯通且向后兼容。
